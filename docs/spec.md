## 1. 배경과 목표

### 1.1 회사와 도메인
- (주)잡자재: 패시브하우스용 열회수 환기장치(KOMFOVENT DOMEKT R 300V/450V/700V), 복사냉방, 기밀·단열 자재를 유통한다.
- 기술 서비스: TAB(풍량 측정·조정), 블로어도어 테스트(기밀), WUFI 시뮬레이션, 웹 환기량 산정 계산기.
- 자체 하드웨어: **VEMC(Ventilation Energy Management Controller)**. 주방 후드나 화장실 배기팬이 켜지면 환기장치에 신호를 보내 급기를 올리고 배기를 내려 실내 압력 균형을 유지한다.
- 공고의 주요 업무: IoT & BEMS 플랫폼 개발, 모바일 서비스 런칭, 사내 엔지니어링 자동화, 시스템 안정성 확보.

### 1.2 풀려는 문제
설치된 환기장치는 고객이 문제를 느끼고 문의하기 전까지 상태를 알 수 없다. A/S는 게시판 문의 후 사람이 원인을 추측하는 방식이다.

### 1.3 MVP 목표
1. 현장에 설치된 환기장치와 VEMC의 상태를 원격으로 수집하고 저장한다.
2. 필터 막힘, 풍량 부족, CO2 과다, VEMC 미연동, 장비 오프라인을 자동으로 감지해 알린다.
3. 앱(웹)에서 환기장치 부스트를 원격으로 요청하고, 적용 여부를 확인한다.
4. 고객의 A/S 신청이 들어오면 측정값을 근거로 AI 소견을 만들고, 직원이 판정한다.
5. `docker compose up` 한 번으로 전체를 실행하고 시연할 수 있다.

### 1.4 범위에서 제외
로그인·권한, 여러 회사(멀티테넌트), 고객 개인정보 관리, 실제 장비 연동(Modbus), 펌웨어 업데이트(OTA), 슬랙·카카오 알림, 네이티브 모바일 앱.

## 3. 전체 구조

```
┌─────────────────── 현장 (site) ───────────────────┐
│  주방 후드 ──전선──▶ VEMC ──전선──▶ 환기장치        │  ① 현장 연동 (인터넷 불필요)
│                       │               │            │
│                       └──── 게이트웨이 ┘            │  현장마다 1개, MQTT 클라이언트
│                         (로컬 버퍼 보유)            │
└──────────────────────────┬─────────────────────────┘
                           │ MQTT over TCP (인터넷)    ② 보고·원격 제어
                           ▼
                     [MQTT 브로커]
                           │
                           ▼
         [Spring Boot 앱 — server/, 패키지 vent, 기능별 하위 패키지 (ADR-0008)]
           ├─ site       : 현장·게이트웨이·장비 조회, 게이트웨이 연결 상태
           ├─ telemetry  : 측정값 수신, 검증, 중복 제거, 저장
           ├─ anomaly    : 규칙 평가, 이상 생성·해제
           ├─ command    : 원격 명령 발행, 응답·시간초과 처리
           └─ service    : A/S 신청, 상황 요약, AI 소견, 검증, 판정
           (각 기능 안은 controller / service / repository / domain / dto(request, response) 레이어로 나눈다. CLAUDE.md Coding standards)
                           │
                           ▼
                     [PostgreSQL]
```

### 3.1 역할 분리 원칙
- **안전과 관련된 제어는 현장에서 처리한다.** 후드 연동(VEMC)은 서버를 거치지 않는다. 인터넷이 끊겨도 동작해야 하기 때문이다.
- **클라우드는 감시, 기록, 편의 기능을 맡는다.** 연동이 실제로 일어났는지 확인하고, 사용자의 원격 부스트 요청을 전달한다.
- **장비가 최종 판단한다.** 서버 명령은 요청일 뿐이며, 장비는 자기 보호 로직(동결 방지, 풍량 한계)에 걸리면 거절할 수 있다.

### 3.2 앱을 하나로 두는 이유
1인 개발, 4일 일정, 11명 회사 규모에서 마이크로서비스는 오버스펙이다. 기능별 패키지로 경계를 나눠두고, 장비 수가 늘면 ingest만 분리한다.

### 3.3 가상 장비(시뮬레이터)의 역할
실제 구조의 **현장 게이트웨이**를 흉내 낸다. 시뮬레이터 하나가 현장 3곳을 표현하고, 현장마다 MQTT 연결 1개를 가진다.
- 30초마다 환기장치 측정값을 발행한다.
- 후드 ON/OFF 시나리오를 실행하고, VEMC 연동을 **시뮬레이터 내부에서** 처리한다(브로커를 거치지 않음).
- 시나리오 주입: 필터 막힘, CO2 상승, VEMC 고장, 장비 오프라인, 시계 오차.
- 브로커 연결이 끊기면 로컬 버퍼에 쌓았다가 재연결 후 업로드한다.

## 4. MQTT 설계

### 4.1 토픽

| 토픽 | 방향 | QoS | retained | 내용 |
|---|---|---|---|---|
| `jabjaje/{siteId}/{deviceId}/telemetry` | 장비 → 서버 | 1 | 아니오 | 측정값 |
| `jabjaje/{siteId}/{deviceId}/event` | 장비 → 서버 | 1 | 아니오 | HOOD_ON, HOOD_OFF 등 |
| `jabjaje/{siteId}/{deviceId}/command` | 서버 → 장비 | 1 | **절대 사용 안 함** | 원격 명령 |
| `jabjaje/{siteId}/{deviceId}/command/ack` | 장비 → 서버 | 1 | 아니오 | 명령 처리 결과 |
| `jabjaje/{siteId}/{gatewayId}/status` | 게이트웨이 → 서버 | 1 | 예 | `online` / `offline`(Last Will) |

- 서버 구독: `jabjaje/+/+/telemetry`, `jabjaje/+/+/event`, `jabjaje/+/+/command/ack`, `jabjaje/+/+/status`.
- 게이트웨이는 장비가 아니므로 `gateway` 테이블에 따로 저장한다(예: `gw-s1`). 게이트웨이가 연결되지 않은 동안 그 현장의 장비는 `확인 불가`로 표시한다. 장비가 멈췄다는 뜻이 아니다.
- command 토픽에 retained를 쓰지 않는 이유: 재접속할 때 오래된 명령이 다시 실행되는 것을 막기 위해서다.

### 4.2 메시지 형식

측정값:
```json
{
  "messageId": "uuid",
  "deviceId": "vent-h1",
  "measuredAt": "2026-10-24T10:00:00+09:00",
  "co2Ppm": 820, "tempC": 23.4, "humidityPct": 48,
  "supplyCmh": 180, "exhaustCmh": 175,
  "filterPa": 85, "bypass": false
}
```

이벤트:
```json
{ "messageId": "uuid", "deviceId": "vemc-h1", "type": "HOOD_ON", "occurredAt": "..." }
```

원격 명령:
```json
{
  "commandId": "uuid",
  "type": "BOOST",
  "params": { "supplyCmh": 260, "exhaustCmh": 250, "durationSec": 1800 },
  "issuedAt": "...",
  "expiresAt": "..."
}
```

명령 응답:
```json
{ "commandId": "uuid", "result": "APPLIED", "appliedAt": "..." }
{ "commandId": "uuid", "result": "REJECTED", "reason": "FROST_PROTECTION" }
```

### 4.3 신뢰성 규칙
- **중복**: QoS 1은 최소 한 번 전달이라 중복이 올 수 있다. `messageId`(측정값·이벤트), `commandId`(응답)로 걸러낸다.
- **신원**: 장비 ID는 **토픽에서 읽는다.** payload의 `deviceId`가 토픽과 다르면 거절한다. 브로커 ACL이 토픽 단위로 권한을 묶기 때문에 토픽이 더 믿을 수 있다.
- **명령 멱등성**: 장비는 최근 처리한 `commandId`를 기억하고, 같은 ID가 다시 오면 다시 적용하지 않고 이전 결과만 응답한다.
- **명령 만료**: 장비는 `expiresAt`이 지난 명령을 무시한다. 오프라인 동안 쌓인 명령이 몇 시간 뒤에 실행되는 것을 막는다.
- **자동 복귀**: 부스트는 `durationSec`가 지나면 장비가 스스로 원래대로 돌아간다. 해제 명령이 유실돼도 계속 켜져 있지 않다.
- **세션 유지**: 서버는 persistent session(clean start = false)과 QoS 1로 구독한다. 서버가 재시작되는 동안 들어온 메시지는 브로커가 보관한다.
- **재접속**: 게이트웨이는 지수 백오프와 무작위 지연(jitter)으로 재접속한다. 브로커가 재시작될 때 모든 장비가 동시에 접속하는 것을 막는다.

### 4.4 버전 호환
현장에는 업데이트 시점이 다른 게이트웨이가 섞여 있다. 서버는 여러 버전을 동시에 받아야 한다.
- 모든 메시지에 `schemaVersion`을 넣는다.
- 게이트웨이는 `online` 상태 메시지에 자기 버전과 지원 기능을 보고한다.
  ```json
  { "state": "online", "firmwareVersion": "1.2.0", "schemaVersion": 1,
    "capabilities": ["BOOST", "HOOD_EVENT"] }
  ```
- 서버는 `capabilities`에 없는 명령을 보내지 않는다. 대시보드도 지원하지 않는 기능의 버튼을 숨긴다.
- 메시지 형식 변경은 **필드 추가만** 허용한다. 서버는 모르는 필드를 무시한다. 필드 삭제나 의미 변경이 필요하면 `schemaVersion`을 올리고, 구버전 게이트웨이가 남아 있는 동안 두 버전을 함께 처리한다.
- 이상 기준, 규칙, AI 소견, 화면처럼 판단이 들어가는 로직은 서버에 둔다. 게이트웨이는 측정·전달·명령 적용·현장 연동만 한다. 기능 변경 대부분이 서버 배포로 끝나게 하기 위해서다.
- `gateway` 테이블에 `firmware_version`, `capabilities`(jsonb)를 둔다(5장, V7). 버전을 보고하는 것은 게이트웨이다.

### 5.2 데이터 검증 (ingest)
- 범위 밖 값(CO2 0 이하 또는 10,000 초과, 습도 0~100 밖, 풍량 음수 등)은 저장하되 `quality = OUT_OF_RANGE`로 표시하고 이상 규칙에서 제외한다.
- `measured_at`이 `received_at`보다 5분 넘게 미래면 `quality = CLOCK_SKEW`로 표시한다.
- `received_at - measured_at`이 2분을 넘으면 `late = true`로 표시한다(버퍼 업로드).
- `device.last_received_at`은 수신 시각 기준으로 갱신한다.

### 5.3 최소 환기량과 목표 풍량
최소 환기량은 회사 환기량 산정 기준을 따른다.
- 인원 기준: 거주 인원 × 30 CMH
- 면적 기준: 바닥면적 × 층고 2.5m × 0.6회/h
- 둘 중 큰 값을 **정수로 올림**한다 (예: 148.5 → 149). 최소 환기량보다 적게 잡히지 않게 하기 위해서다.

목표 풍량은 TAB으로 맞춘 값이 있으면 그 값이고, 없으면 최소 환기량과 같다. `AIRFLOW_BELOW_TARGET` 이상은 목표 풍량과 비교한다.

## 6. 이상

### 6.1 규칙

| 규칙 | 발생 | 해제 | 심각도 |
|---|---|---|---|
| `CO2_HIGH` | 1,000ppm 초과가 10분 지속 | 900ppm 미만이 10분 지속 | WARN, 1,500ppm 초과면 CRITICAL |
| `FILTER_CLOGGED` | 필터 차압이 모델별 기준 초과 (초기값 150Pa) | 기준보다 20Pa 넘게 낮아짐 (130Pa 미만, 필터 교체) | WARN |
| `AIRFLOW_BELOW_TARGET` | 급기가 목표 풍량의 80% 미만으로 30분 지속 (부스트·바이패스 중 제외) | 80%에 다시 도달 | WARN |
| `BYPASS_TOO_LONG` | 바이패스 60분 넘게 지속 | 바이패스 꺼짐 | WARN |
| `GATEWAY_OFFLINE` | 게이트웨이가 오프라인이 됨 (일시 끊김이 30분 넘게 이어짐). 이상은 게이트웨이에 붙음 | 다시 연결 | WARN |
| `VEMC_NO_RESPONSE` | HOOD_ON 후 60초 안에(측정 시각 기준) 급기가 오르지 않음 | 다음 연동 정상 | WARN |
| `COMMAND_TIMEOUT` | 원격 명령이 재시도 후에도 응답 없음 | 다음 명령 정상 | INFO |

- 게이트웨이 연결은 2단계로 다룬다. 2분 무수신 또는 Last Will이면 **일시 끊김**(`INTERRUPTED`)으로 바꾸고 화면에만 표시한다. 30분이 지나면 **오프라인**(`OFFLINE`)으로 바꾸고 이상을 만든다. 가정용 Wi-Fi의 짧은 끊김마다 이상이 쌓이는 것을 막는다. 상태 변경과 이상은 같은 트랜잭션에서 저장한다(ADR-0014).
- 기준값은 설정 파일에 둔다. 필터 차압 기준은 모델별로 둔다. 실제 기준값은 제조사 매뉴얼로 확인해야 한다.

### 6.2 평가 방식
- 측정값이 들어올 때마다 해당 장비의 규칙을 평가한다. 측정값 저장이 커밋된 뒤 별도 트랜잭션에서 평가해, 평가가 실패해도 측정값은 남는다(ADR-0013). 오프라인 규칙은 30초 주기 스케줄러로 평가한다.
- **시간 판단은 모두 `measured_at` 기준**으로 한다.
- **지금 상태를 나타내는 규칙은 최근 데이터로만 판단한다.** `CO2_HIGH`, `AIRFLOW_BELOW_TARGET`, `BYPASS_TOO_LONG`은 `late = true` 데이터를 쓰지 않는다. 몇 시간 전 데이터로 지금 이상이 뜨는 것을 막는다. `FILTER_CLOGGED`는 `measured_at` 기준 가장 최신 값만 본다.
- **장비 고장 판정은 늦은 데이터도 쓴다.** `VEMC_NO_RESPONSE`는 시간이 지나도 의미가 남는 고장이라, 오프라인 동안의 HOOD_ON 이벤트와 측정값도 함께 평가한다. 끊긴 동안 연동이 정상이었는지 복구 후에 확인할 수 있다.
- `VEMC_NO_RESPONSE` 판정: 30초 주기 스케줄러가 판정되지 않은 HOOD_ON 이벤트를 찾는다. 같은 현장 환기장치의 측정값 중 `occurred_at` + 60초 이후 값이 있으면, 직전 값보다 급기가 올랐는지 확인한다.
- `quality != OK`인 데이터는 규칙 평가에서 제외한다.
- 상태를 메모리에 두지 않고 DB를 조회한다. 서버가 재시작돼도 판단이 이어진다.
- 해제 조건을 발생 조건보다 느슨하게 잡는다(히스테리시스). 기준값 근처에서 이상이 켜졌다 꺼졌다 반복하는 것을 막는다.
- 규칙 하나를 클래스 하나로 만들고, 규칙마다 단위 테스트를 둔다.
- 이상은 대시보드에 표시하고 로그로 남긴다. 사람에게 보내는 알림(슬랙, 카카오 등)은 MVP 범위 밖이다.

### 6.3 오프라인 감지와 화면 표시
감지는 두 경로로 한다. 어느 쪽이든 먼저 걸리면 일시 끊김으로 본다.
- **Last Will**: 게이트웨이 연결이 끊기면 브로커가 keepalive 시간의 1.5배(keepalive 60초면 약 90초) 뒤에 `offline`을 대신 발행한다.
- **무수신 검사**: 30초 주기 스케줄러가 `last_received_at`이 2분 넘게 지난 게이트웨이를 찾는다. 연결 전(`PENDING`) 게이트웨이는 검사하지 않는다. Wi-Fi가 꺼졌는데 TCP 연결이 끊긴 줄 모르는 경우(half-open)에 대비한다.
- **수신으로 보는 것**: 측정값 저장, retained가 아닌 `online`. 서버가 다시 구독할 때 브로커가 보내는 retained `online`은 옛날 메시지라 버전·지원 기능만 기록한다. `offline`은 retained여도 반영한다(서버가 꺼진 동안 Last Will이 나갔다는 뜻).
- **끊긴 시각**(`disconnected_at`)은 끊긴 것을 알아챈 시각이 아니라 마지막 수신 시각이다. Last Will은 실제로 끊긴 뒤 keepalive의 1.5배가 지나서 온다. 30분 판정과 "오프라인 N분"은 이 시각 기준이다.
- 2분, 30분, 검사 주기는 `vent.gateway.connection` 설정이다. 시연 때는 `VENT_GATEWAY_OFFLINE_AFTER=3m docker compose up -d`처럼 줄인다.

| 단계 | 조건 | 직원 대시보드 | 고객 화면 |
|---|---|---|---|
| 연결 전 (`PENDING`) | 등록 후 아직 한 번도 수신 없음 | 회색 "연결 전 · 아직 받은 적 없음" 배지, 장비는 `확인 불가`. 이상을 만들지 않는다 | "설치가 끝나면 상태가 표시돼요." |
| 연결됨 (`CONNECTED`) | 마지막 수신 2분 이내 | 초록 배지, 실시간 값 | 실시간 값 |
| 일시 끊김 (`INTERRUPTED`) | 2~30분 | 게이트웨이에 회색 "일시 끊김 · 마지막 수신 N분 전" 배지, 장비는 `확인 불가`로 마지막 값을 흐리게 표시, 그래프 빈 구간 음영, 부스트 버튼 비활성화. **이상 목록에는 올리지 않는다** | "연결이 잠시 끊겼어요. 환기장치는 집 안에서 계속 동작 중이에요." |
| 오프라인 (`OFFLINE`) | 30분 넘게 | 위 표시 + 이상 목록에 `GATEWAY_OFFLINE`(WARN). A/S 담당 확인 대상 | "연결이 끊긴 지 30분이 넘었어요. 집 Wi-Fi를 확인해 주세요." |
| 복구 | 다시 수신 | 초록 배지, 끊긴 구간을 늦은 측정값으로 채움(그래프에서 다른 색으로 구분), 이상 자동 해제, 이력에 "오프라인 47분" 기록 | 실시간 값 |

## 7. 원격 명령

### 7.1 흐름
1. 사용자가 대시보드에서 부스트를 요청한다.
2. 서버가 게이트웨이 상태를 확인한다. `CONNECTED`가 아니면(일시 끊김, 오프라인) 명령을 보내지 않고 `REJECTED_OFFLINE`으로 기록한 뒤 "지금은 연결이 끊겨 명령을 보낼 수 없어요"로 안내한다.
3. 서버가 파라미터를 검증한다. 풍량은 모델 최대 풍량 이하, 지속시간은 최대 2시간 이하.
4. `command`를 `SENT`로 저장하고 발행한다. `expiresAt`은 발행 후 60초다.
5. 장비는 만료, 중복, 자기 보호 로직을 확인한 뒤 적용하거나 거절하고 응답한다.
6. 서버는 응답을 받아 `APPLIED` 또는 `REJECTED`로 바꾼다.
7. 10초 동안 응답이 없으면 같은 `commandId`로 1회 재시도한다. 그래도 없으면 `TIMEOUT`으로 바꾸고 `COMMAND_TIMEOUT` 이상을 만든다.

### 7.2 명령이 한꺼번에 몰릴 때
게이트웨이가 연결되지 않으면 서버가 명령을 보내지 않지만, 일시 끊김이 감지되기 전(끊긴 직후 최대 2분)에 보낸 명령은 브로커에 쌓였다가 재연결 때 한꺼번에 도착할 수 있다. 세 곳에서 막는다.

**서버**
- 장비당 대기 중(`SENT`) 명령은 하나만 둔다. 새 명령이 오면 이전 대기 명령은 `SUPERSEDED`로 바꾼다.
- 명령은 "실행할 동작"이 아니라 "원하는 상태"로 다룬다. `BOOST(풍량, 지속시간)`과 `BOOST_CANCEL`은 마지막 것만 의미가 있다.

**브로커**
- MQTT 5의 Message Expiry Interval을 60초로 설정한다. 만료된 명령은 브로커가 장비에 전달하지 않고 버린다.
- 브로커나 클라이언트가 MQTT 3.1.1만 지원하면 장비의 `expiresAt` 검사로만 막는다.

**장비(게이트웨이)**
1. `expiresAt`이 지난 명령은 버리고 `REJECTED`(사유 `EXPIRED`)로 응답한다.
2. 이미 처리한 `commandId`는 다시 적용하지 않는다.
3. 남은 명령 중 `issuedAt`이 가장 최신인 것 하나만 적용하고, 나머지는 `REJECTED`(사유 `SUPERSEDED`)로 응답한다.

**늦은 응답**
- 서버가 `TIMEOUT`으로 처리한 뒤에 `APPLIED` 응답이 오면, 실제 결과대로 `APPLIED`로 바꾸고 `late_ack = true`로 표시한다.
- 이때 `COMMAND_TIMEOUT` 이상도 해제한다. 화면에는 "늦게 적용됨"으로 보여준다.

**확장 방향**: 장비가 많아지면 디바이스 섀도(AWS IoT Device Shadow, Azure Device Twin과 같은 개념)로 바꾼다. 서버는 "원하는 상태(desired)"만 저장하고, 장비는 "현재 상태(reported)"를 보고한다. 재연결 시 장비는 최신 desired 상태 하나만 받아 맞춘다.

### 7.3 우선순위 (장비에서 판단)
1. 장비 자기 보호 로직(동결 방지, 풍량 한계)
2. 현장 VEMC 연동
3. 사용자 원격 명령

### 7.4 부스트는 급기와 배기를 함께 올린다
급기만 올리면 실내가 과도한 양압이 되어 문틈 소음, 벽체 내부 결로 위험이 생긴다. 원격 부스트는 급·배기 균형을 유지한 채 함께 올린다. 급기를 올리고 배기를 내리는 것은 후드가 켜졌을 때 VEMC만 한다.

## 8. A/S 신청과 AI 소견

### 8.1 흐름
1. 고객의 A/S 신청을 `service_request`로 저장한다(`RECEIVED`). 고객에게는 즉시 접수 완료를 응답한다.
2. 백그라운드에서 상황 요약을 만든다(코드). 장비 목록, 최근 7일 측정값 통계, 열린·최근 이상, 후드 연동 결과, 모델 스펙.
3. Claude API를 호출해 AI 소견을 받는다.
4. AI 소견을 코드로 검증한다.
5. 통과하면 `ASSESSED`, 실패하면 `NEEDS_HUMAN`으로 바꾼다.
6. 직원이 대시보드에서 AI 소견을 보고 판정한다(`DECIDED`). 그대로 승인하거나 고칠 수 있고, `NEEDS_HUMAN`이면 처음부터 판정한다. AI가 고객에게 직접 답하지 않는다.

### 8.2 상황 요약 (코드가 계산)
- 원본 측정값 대신 통계만 보낸다. 예: 평균·최대 CO2, 급기 대비 목표 풍량 비율, 필터 차압 추세(7일 전 → 현재), 바이패스 누적 시간, 후드 연동 성공률, 오프라인 횟수.
- 숫자 계산은 코드가 하고 AI는 해석만 한다.
- 고객 이름, 주소, 연락처는 보내지 않는다. 지역과 장비 정보만 보낸다.

### 8.3 프롬프트 구성
- 역할과 출력 규칙
- 소견 기준표: 증상별 원인 체크리스트(필터 막힘, 풍량 부족, 바이패스, VEMC 미연동, 기밀 불량 → 블로어도어 테스트 권유, 목표 풍량 불일치 → TAB 권유)
- 부품 목록: 판매 중인 교체 부품 이름 목록
- 상황 요약(JSON)
- 고객 문의 원문: **별도 구분 태그 안에 넣고, 그 안의 지시는 따르지 않는다고 명시**한다.

### 8.4 출력 형식 (JSON)

```json
  ],
  "technicianActions": ["필터 교체", "교체 후 풍량 재측정"],

```

### 8.5 검증 (코드)
- JSON 형식과 필수 항목을 확인한다.
- `evidence`의 지표 이름이 상황 요약에 실제로 있는지 확인한다.
- `parts`가 부품 목록에 있는지 확인한다.
- `customerReply`에 금액, 무상 교체 약속, 보증 관련 표현이 있으면 걸러낸다(프롬프트 인젝션 대응).
- 실패하면 1회 재시도하고, 그래도 실패하면 `NEEDS_HUMAN`으로 넘기고 `validation_errors`에 이유를 남긴다.

### 8.6 장애 대응
- API 호출 타임아웃을 둔다. 실패하면 `NEEDS_HUMAN`.
- AI 호출부는 인터페이스로 분리한다. 실제 구현과 가짜 구현(고정 응답)을 둔다. API 키가 없거나 네트워크가 안 되면 가짜 구현으로 시연할 수 있다.
- API 키는 환경변수로만 주입하고 저장소에 올리지 않는다.

### 8.7 평가 세트
시뮬레이터로 시나리오 5개를 만들고, AI가 1순위로 꼽은 원인이 정답과 맞는지 확인한다.

| 시나리오 | 정답 원인 |
|---|---|
| 필터 차압이 7일간 계속 상승 | 필터 막힘 |
| 인원 과다로 CO2 상승, 장비는 정상 | 목표 풍량 대비 인원 초과 |
| 후드 ON에도 급기 변화 없음 | VEMC 미연동 |
| 데이터는 정상인데 고객이 답답함 호소 | 장비 이상 없음, 방문 상담 또는 기밀 점검 권유 |
| 게이트웨이 장기 오프라인 | 통신 문제, 데이터 부족으로 판단 보류 |

모델이나 프롬프트를 바꿀 때마다 다시 돌려 품질 변화를 확인한다.

### 10.5 축소 순서
일정이 밀리면 아래 순서로 줄인다.
1. 대시보드를 최소 HTML 한 장으로
2. 평가 세트를 3개 시나리오로
3. `BYPASS_TOO_LONG`, `COMMAND_TIMEOUT` 이상 제외
4. 브로커 ACL을 문서화로 대체

줄이지 않는 것: 수집·저장 흐름, 중복 제거, 오프라인 버퍼 시연, AI 출력 검증, 이상 규칙 단위 테스트.

---

## 11. 테스트 전략
- 단위 테스트: 이상 규칙별, 목표 풍량 계산, 데이터 검증(범위, 시계 오차, 늦은 도착), AI 출력 검증기(엉터리 부품, 없는 근거, 금지 표현).
- 통합 테스트: 실제 PostgreSQL과 브로커(컨테이너)를 띄워 측정값 발행 → 저장 → 이상 생성까지 확인. 중복 메시지 두 번 발행 시 한 건만 저장되는지 확인.
- 시나리오 테스트: 브로커 중지 → 후드 ON → 브로커 재시작 → 늦은 데이터 저장, 실시간 이상 미생성, 연동 결과 확인.
- AI 평가 세트: 8.7.

## 12. 시연 시나리오
1. 대시보드에서 현장 3곳의 실시간 상태 확인
2. 필터 막힘 시나리오 주입 → `FILTER_CLOGGED` 이상
3. 원격 부스트 → `APPLIED` 확인
4. 브로커 중지(인터넷 끊김) → 후드 ON → 시뮬레이터 로그에서 급기 상승 확인 → 브로커 재시작 → 끊긴 구간 데이터가 채워짐
5. A/S 신청 등록 → AI 소견과 근거 → 검증 결과 → 직원 판정
