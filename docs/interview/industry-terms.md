# 현업 용어 사전

2026-10-23까지 만든 코드(#1, #2)에 나온 현업 용어를 모았다. 각 용어는 **한 줄 뜻 → 우리 코드에서 어디 → 면접에서 한마디** 순서다.
도메인 용어(현장, 장비, 이상 등)는 [GLOSSARY.md](../../GLOSSARY.md), 흐름은 [code-walkthrough.md](code-walkthrough.md)를 본다.

---

## 1. 구조와 레이어

| 용어 | 한 줄 뜻 | 우리 코드 | 면접 한마디 |
|---|---|---|---|
| 레이어드 아키텍처 | 요청 처리 → 업무 로직 → 데이터 접근을 층으로 나누는 구조 | controller / service / repository / domain | "기능별로 묶고 그 안에서 레이어를 나눴다" |
| 기능별 패키지 (package by feature) | 레이어가 아니라 기능 단위로 먼저 묶는 방식 | `vent/site`, `vent/telemetry` | 기능 하나를 고칠 때 한 폴더만 보면 된다 |
| 인바운드 어댑터 | 외부 입력(HTTP, 메시지)을 받아 내부 로직으로 넘기는 입구 | `SiteController`, `TelemetryMqttListener` | 입구는 해석만 하고 판단은 서비스에 맡긴다 |
| 유스케이스 (서비스) | 사용자 관점의 작업 하나를 처리하는 단위 | `TelemetryIngestService.ingest()` | 트랜잭션 경계가 여기다 |
| DTO | 계층·시스템 사이에서 데이터를 옮기는 그릇 | `dto/request`, `dto/response` | 엔티티를 그대로 내보내지 않아 API가 DB 구조에 묶이지 않는다 |
| 엔티티 | DB 테이블 한 행에 대응하는 객체 | `Site`, `Gateway`, `Device`, `Telemetry` | 테이블마다 파일 하나 |
| 리포지토리 | 저장소 접근을 감춘 인터페이스 | `SiteRepository`, `TelemetryRepository` | 서비스는 SQL을 모른다 |
| ADR | 되돌리기 어려운 설계 결정과 이유를 짧게 남긴 문서 | `docs/adr/0001~0011` | "왜 이렇게 했나"를 문서로 답할 수 있다 |
| 멀티 모듈 | 한 저장소에 빌드 단위를 여러 개 두는 것 | `server/`, `simulator/`, `web/` | 진입점(main)마다 모듈을 나눴다 |

## 2. 메시징 (MQTT)

| 용어 | 한 줄 뜻 | 우리 코드 | 면접 한마디 |
|---|---|---|---|
| 발행/구독 (pub/sub) | 보내는 쪽과 받는 쪽이 서로 모르고 브로커만 아는 방식 | 시뮬레이터 → Mosquitto → 서버 | 장비가 먼저 연결하니 NAT 뒤에도 명령을 보낼 수 있다 |
| 브로커 | 메시지를 받아 구독자에게 나눠 주는 서버 | Mosquitto 2 (ADR-0007) | 운영에서는 이중화가 필요하다(단일 장애점) |
| 토픽 / 토픽 필터 | 메시지 주소 / 와일드카드(`+`, `#`)로 여러 토픽을 받는 패턴 | `jabjaje/+/+/telemetry` | 장비 ID를 토픽에서 읽어 ACL과 맞춘다 |
| QoS 0/1/2 | 전달 보장 수준(최대 한 번 / 최소 한 번 / 정확히 한 번) | QoS 1 | 1은 중복이 올 수 있어 멱등 저장과 함께 쓴다 |
| PUBACK | QoS 1에서 받는 쪽이 보내는 "받았음" 응답 | Paho가 자동 전송 | 저장 실패에도 보내면 유실 → manual ack(#3) |
| 영속 세션 (clean start = false) | 연결이 끊긴 동안의 메시지를 브로커가 보관 | `MqttClientManager` | 서버 재시작 중 메시지도 받는다 |
| Last Will | 비정상 종료 때 브로커가 대신 보내 주는 메시지 | #6에서 사용 | 오프라인 감지에 쓴다 |
| 직렬화 / 역직렬화 | 객체 ↔ 바이트(JSON) 변환 | Jackson | 모르는 필드는 무시한다(관대한 수신) |
| 관대한 수신 (tolerant reader) | 모르는 필드가 와도 깨지지 않게 받는 원칙 | `TelemetryMessage` (ADR-0004) | 구버전·신버전 게이트웨이가 섞여도 동작한다 |
| 스키마 버전 | 메시지 형식 버전 번호 | `schemaVersion` | 필드 삭제·의미 변경 때만 올린다 |

## 3. 데이터와 DB

| 용어 | 한 줄 뜻 | 우리 코드 | 면접 한마디 |
|---|---|---|---|
| 스키마 마이그레이션 | DB 구조 변경을 버전 파일로 관리 | Flyway `V1`, `V3` | 어떤 DB든 같은 순서로 같은 구조가 된다 |
| 체크섬 | 파일 내용의 지문. 바뀌면 값이 달라진다 | Flyway 검증 | 적용된 파일은 고치지 않고 새 버전을 추가한다 |
| 반복 실행 마이그레이션 (`R__`) | 내용이 바뀔 때마다 다시 실행되는 마이그레이션 | `R__demo_seed.sql` | 멱등하게 써야 한다 |
| 시드 데이터 | 초기·시연용으로 넣는 데이터 | demo 프로필 전용 (ADR-0011) | 운영 DB에 가짜 데이터가 들어가지 않게 분리했다 |
| 프로필 | 환경(운영, 시연, 테스트)별 설정 묶음 | `application-demo.yml` | 같은 코드, 다른 설정 |
| 유니크 제약 | 같은 값이 두 번 들어가지 못하게 하는 DB 규칙 | `telemetry.message_id` | 중복 제거를 DB가 보장 |
| `ON CONFLICT DO NOTHING` | 충돌하면 조용히 건너뛰는 PostgreSQL INSERT | `TelemetryInsertRepositoryImpl` | 영향받은 행 0/1로 중복을 안다 |
| 복합 외래키 | 컬럼 여러 개를 묶어 다른 테이블을 참조 | `(gateway_id, site_id)` | "장비의 현장 = 게이트웨이의 현장"을 DB가 보장 |
| 복합 인덱스 | 여러 컬럼을 묶은 검색 색인 | `(device_id, measured_at DESC)` | 장비별 최신값 조회가 빠르다 |
| `DISTINCT ON` | 그룹마다 첫 행만 고르는 PostgreSQL 문법 | `findLatestPerDevice()` | 장비별 최신 1건을 한 쿼리로 |
| timestamptz / UTC | 시간대를 고려한 시각 타입 / 기준 시간대 | 저장·응답은 UTC, 화면은 한국 시간 | 서버 위치와 상관없이 같은 값 |
| N+1 문제 | 목록 1번 + 항목마다 1번씩 쿼리가 더 나가는 문제 | `@EntityGraph`로 해결 | 현장 목록이 쿼리 한 번 |
| 엔티티 그래프 / 페치 조인 | 연관된 엔티티를 한 번에 함께 가져오는 방법 | `SiteRepository` | N+1 해결책 |
| 더티 체킹 | 트랜잭션 안에서 엔티티 필드를 바꾸면 끝날 때 자동으로 UPDATE | `device.markReceived()` | UPDATE 문을 직접 쓰지 않았다 |
| 영속성 컨텍스트 | JPA가 트랜잭션 동안 엔티티를 관리하는 공간 | 서비스 트랜잭션 | 더티 체킹이 여기서 일어난다 |
| open-in-view | 화면 렌더링까지 DB 연결을 유지하는 Spring 기본 설정 | `false`로 끔 | 트랜잭션 밖 지연 로딩을 막는다 |
| `ddl-auto: validate` | 엔티티와 스키마가 맞는지 시작할 때만 확인 | `application.yml` | 이름 규칙 실수(`co2ppm`)를 시작 시점에 잡았다 |

## 4. 신뢰성

| 용어 | 한 줄 뜻 | 우리 코드 | 면접 한마디 |
|---|---|---|---|
| 멱등성 | 같은 요청을 여러 번 해도 결과가 한 번과 같음 | messageId 중복 무시, 멱등 시드 | "최소 한 번 전달 + 멱등 처리" |
| 최소 한 번 전달 (at-least-once) | 유실은 없지만 중복은 있을 수 있는 전달 | QoS 1 | 중복은 받는 쪽이 걸러낸다 |
| 지수 백오프 | 재시도 간격을 2배씩 늘리는 방식 | 서버 첫 연결 1초 → 최대 30초 | 상대가 회복할 시간을 주고 폭주를 막는다 |
| 준비 상태 (readiness) | 요청을 받을 준비가 끝났는지 | `isReady()` | 헬스 체크로 확장 가능 |
| 위조 방지 | 남의 신원을 사칭한 데이터를 거르는 것 | 토픽 장비 ID ≠ 메시지 장비 ID → 거절 | ACL이 묶는 토픽을 믿는다 |
| 수동 확인 응답 (manual ack) | 처리를 끝낸 뒤에만 "받았음"을 보내는 방식 | #3에서 적용 예정 | DB 장애 때 유실을 막는다 |

## 5. 테스트

| 용어 | 한 줄 뜻 | 우리 코드 | 면접 한마디 |
|---|---|---|---|
| TDD (red → green) | 실패하는 테스트를 먼저 쓰고, 통과할 만큼만 구현 | 404로 실패 → 구현 → 통과 | "올바른 이유로 실패"하는지부터 본다 |
| 통합 테스트 | 여러 부품을 실제로 연결해 확인하는 테스트 | MQTT 발행 → DB → API | 가짜(mock) 대신 진짜 브로커·DB |
| Testcontainers | 테스트가 Docker 컨테이너를 띄워 쓰는 라이브러리 | PostgreSQL, Mosquitto | 로컬과 CI에서 같은 환경 |
| 플래키 테스트 | 같은 코드인데 성공·실패가 들쭉날쭉한 테스트 | 구독 전 발행 문제 | 준비 상태를 기다려 결정적으로 만들었다 |
| Awaitility | 비동기 결과를 "조건이 맞을 때까지" 기다리는 도구 | `await().untilAsserted(...)` | 고정 sleep 대신 쓴다 |
| 보초(sentinel) 메시지 | 앞의 처리가 끝났음을 알려 주는 마지막 메시지 | 중복·거절 테스트 | "없음"을 확실하게 확인 |

## 6. 빌드와 실행

| 용어 | 한 줄 뜻 | 우리 코드 | 면접 한마디 |
|---|---|---|---|
| 빌드 래퍼 | 설치 없이 정해진 버전으로 빌드하게 하는 스크립트 | `gradlew` | 누구 PC에서나 같은 Gradle |
| 툴체인 | 빌드 도구를 돌리는 Java와 컴파일하는 Java를 분리 | Gradle 9(Java 25) + 컴파일 Java 17 | ADR-0006 |
| 멀티 스테이지 빌드 | 빌드용 이미지와 실행용 이미지를 나누는 Dockerfile | `server/Dockerfile` 3단계 | 실행 이미지에 빌드 도구가 없다 |
| 헬스체크 | 컨테이너가 정상인지 주기적으로 확인 | postgres `pg_isready` | 앱은 DB가 준비된 뒤 뜬다 |
| 라이프사이클 빈 | 앱 시작·종료 때 같이 시작·정리되는 빈 | `MqttClientManager` (`SmartLifecycle`) | 종료 때 연결을 정리한다 |

## 7. 화면 (React)

| 용어 | 한 줄 뜻 | 우리 코드 | 면접 한마디 |
|---|---|---|---|
| SPA | 페이지 하나에서 화면을 바꾸는 웹 앱 | `web/` | |
| 컴포넌트 | 화면을 이루는 재사용 단위 | `SiteCard`, `ConnectionBadge` | |
| 상태 / 부수 효과 | 화면이 기억하는 값 / 렌더링 밖에서 하는 일(API 호출, 타이머) | `useState`, `useEffect` | 화면이 사라질 때 타이머 정리 |
| 폴링 | 일정 간격으로 다시 물어보는 방식 | 30초마다 API 호출 | 측정 주기가 30초라 충분 |
| 개발 프록시 | 개발 서버가 API 요청을 백엔드로 넘겨 주는 것 | `vite.config.ts` | |
| CORS | 다른 주소의 API 호출을 브라우저가 막는 규칙 | 주소를 하나로 합쳐 필요 없음 | ADR-0010 |
| 정적 리소스 서빙 | 빌드된 HTML·JS를 서버가 그대로 내려주는 것 | Spring Boot `static/` | 배포 단위가 하나 |
| API 계약 (타입) | 서버 응답 형태를 타입으로 고정한 것 | `web/src/types` | 서버가 바뀌면 화면에서 컴파일 오류 |
