| 블로어도어 테스트 | 건물 기밀 성능 측정 | AI 진단에서 기밀 불량 의심 시 권유 |

## 측정값 7가지 (#43)

| 항목 | 단위 | 판단에 쓰는 곳 |
|---|---|---|
| CO2 농도 | ppm (실내 600~1,000이 보통) | 환기 충분한지 → `CO2_HIGH` |
| 실내 온도 | ℃ | 쾌적성, AI 소견 참고 |
| 실내 습도 | % (40~60% 쾌적) | 결로·곰팡이 위험, AI 소견 참고 |
| 급기 풍량 | CMH | 목표 풍량 비교 → `AIRFLOW_BELOW_TARGET`, 후드 연동 확인 |
| 배기 풍량 | CMH | 급기와 균형(양압·음압) |
| 필터 차압 | Pa (막힐수록 커짐) | 필터 교체 → `FILTER_CLOGGED` |
| 바이패스 여부 | 켜짐/꺼짐 | 오래 켜지면 장비 에러 → `BYPASS_TOO_LONG` |

- 측정값(30초마다 상태) ≠ 이벤트(후드 ON/OFF처럼 일이 생길 때 한 번)
- 핵심 가치: 필터 차압이 오르고 급기가 떨어지는 추세를 보고, 고객이 "답답하다"고 문의하기 전에 알아챈다

## 통신

**MQTT** (#5)
- 브로커를 가운데 둔 발행(publish)/구독(subscribe) 방식
- 토픽 = 채널 이름, `+`와 `#` 와일드카드
- 장비가 먼저 연결하므로 NAT 뒤 장비에도 명령 가능

**QoS** (#5, #7)
- 0: 최대 한 번, 1: 최소 한 번(중복 가능), 2: 정확히 한 번
- QoS 1 + 멱등 처리(messageId)가 실무에서 흔한 조합

**Last Will** (#5, #12)
- 클라이언트가 비정상으로 끊기면 브로커가 미리 맡겨둔 메시지를 대신 발행
- keepalive의 1.5배 시간 뒤 발동

**retained 메시지** (#11)
- 브로커가 토픽의 마지막 메시지를 보관했다가 새 구독자에게 바로 준다
- 상태(online/offline)에는 좋고, 명령에는 쓰면 안 된다(재접속 시 옛 명령 재실행)

**persistent session** (#11)
- 연결이 끊긴 동안의 QoS 1 메시지를 브로커가 보관

**MQTT 5 Message Expiry** (#12)
- 메시지에 유효 시간을 붙여, 지나면 브로커가 전달하지 않고 버린다

**Modbus** (#5)
- 산업 장비 통신 규격. 실제 환기장치는 Modbus → 게이트웨이 → MQTT 구조가 일반적

**OSI 7계층과 프로젝트** (#10)
| 계층 | 프로젝트에서 |
|---|---|
| 7 응용 | MQTT, HTTP |
| 4 전송 | TCP (연결 끊김 감지, half-open 문제) |
| 3 네트워크 | IP, NAT(공유기 뒤 장비에 직접 접속 불가) |
| 1~2 물리·데이터링크 | Wi-Fi/이더넷, 후드-VEMC-환기장치 전선 신호, RS-485 |

**게이트웨이는 계층이 아니라 기기** (#28)
- 현장마다 하나 있는 작은 컴퓨터. 집 안쪽은 Modbus(RS-485 전선), 바깥쪽은 MQTT(TCP/IP, Wi-Fi)로 말한다
- 7계층에서 Modbus → MQTT로 바꿔주는 **응용 계층 게이트웨이**. 내용을 바꾸지 않고 전달만 하는 공유기(3계층), 스위치(2계층)와 다르다
- 데이터에서는 "장비"가 아니라 "연결 통로"로 다룬다. 통로가 끊기면 장비는 "확인 불가"(고장이 아니라 소식을 모르는 상태)

**half-open 연결** (#12)
- 한쪽은 끊겼는데 다른 쪽은 연결된 줄 아는 상태. 그래서 Last Will 외에 무수신 검사도 둔다

## 신뢰성 설계

| 개념 | 한 줄 정의 | 프로젝트에서 |
|---|---|---|
| 멱등성 | 같은 요청을 여러 번 해도 결과가 한 번과 같음 | messageId, commandId (#7, #11) |
| 측정 시각 vs 수신 시각 | 장비가 잰 시각과 서버가 받은 시각을 분리 | 늦은 데이터, 순서 바뀜 대응 (#7) |
| 히스테리시스 | 발생과 해제 기준을 다르게 해 반복 깜빡임 방지 | CO2 1,000 / 900ppm (#8) |
| 지수 백오프 + jitter | 재시도 간격을 늘리고 무작위로 흩뜨림 | 동시 재접속 폭주 방지 (#11) |
| 명령 만료 | 오래된 명령은 실행하지 않음 | `expiresAt` (#11) |
| 자동 복귀 (데드맨) | 해제 명령이 없어도 일정 시간 후 원래대로 | 부스트 `durationSec` (#11) |
| 디바이스 섀도 | 서버는 원하는 상태(desired), 장비는 현재 상태(reported)만 관리 | 명령 몰림의 확장 방향 (#12) |
| 현장 제어 vs 클라우드 | 안전 제어는 현장, 감시·편의는 클라우드 | VEMC 설계 (#8, #9) |
| 하위 호환 | 구버전과 신버전이 함께 동작 | schemaVersion, 필드 추가만 (#15) |
| OTA | 장비 소프트웨어 원격 업데이트. 단계적 배포, 롤백 | 게이트웨이 (#15) |

## 프로젝트 구조 (#33~#36)
- **역도메인 패키지**(`com.회사.제품.기능`): 앞부분(회사)은 외부 배포 라이브러리끼리 이름이 겹치지 않게 하는 장치. 배포하지 않는 실행 앱에는 필요 없다
- **Spring Boot 기본 패키지 금지**: 진입점을 패키지 없이 두면 모든 jar를 컴포넌트 스캔하려 해서 문제가 생긴다 → 최소 한 단계(`vent`)
- **기능별 패키지**: `controller/service/repository` 계층 폴더 대신 `site/`, `telemetry/`처럼 기능 단위로 나누면 깊어지지 않고 용어집과 맞는다
- **모듈 분리**: 진입점(main)이 둘이면 모듈을 나눈다 → `server/`, `simulator/`
- **Gradle 툴체인**: 빌드 도구를 돌리는 Java(25)와 코드를 컴파일하는 Java(17)를 분리할 수 있다

## #1 구현에서 배운 것
- **TDD red → green**: 테스트를 먼저 쓰고 "올바른 이유로" 실패하는지 본다(여기선 API가 없어 404). 그다음 통과할 만큼만 구현한다
- **Testcontainers + @ServiceConnection**: 테스트가 실제 PostgreSQL 컨테이너를 띄우고 접속 정보를 자동으로 연결한다
- **Flyway + `ddl-auto: validate`**: 스키마는 마이그레이션이 만들고, Hibernate는 엔티티가 스키마와 맞는지만 확인한다
- **이미 적용된 마이그레이션을 고치면** Flyway가 체크섬이 다르다며 멈춘다. 배포 전 로컬이면 DB를 지우고 다시, 배포 후라면 새 버전 파일을 추가한다
- **`@EntityGraph`**: 현장 목록과 게이트웨이·장비를 한 쿼리로 가져와 N+1 쿼리를 피한다
- **복합 외래키**: `(gateway_id, site_id) → gateway(id, site_id)`로 "장비의 현장 = 게이트웨이의 현장"을 DB가 보장한다
- **코드 리뷰 두 축**: 표준(규칙·용어·냄새)과 스펙(요구사항)을 따로 봐야 서로 가리지 않는다

## 코딩 규칙 (#40~#41)
- **기능 → 레이어 패키지**: 기능별로 묶고 그 안에서 controller / service / repository / domain / dto로 나눈다. 관련 코드는 한곳에 있고 역할은 폴더로 드러난다
- **트랜잭션은 서비스에서**: 컨트롤러는 요청과 응답만, 트랜잭션 경계와 유스케이스는 서비스가 맡는다
- **엔티티를 응답으로 내보내지 않기**: 응답 DTO(record)로 바꿔서 내보낸다. 엔티티를 바꿔도 API 형태가 흔들리지 않고, 지연 로딩 문제도 피한다
- **@author, @since**: 처음 만든 사람과 날짜만 적고, 수정 이력은 git이 맡는다. 주석 날짜를 계속 고치면 금방 틀어진다

## #2 구현에서 배운 것
- **MQTT 구독 타이밍**: 구독하기 전에 발행된 메시지는 (세션이 없으면) 사라진다. 서버가 "연결 + 구독 완료"를 알려주는 준비 상태가 필요하다
- **PUBACK과 유실**: QoS 1에서 수신 측이 확인 응답을 보내면 브로커는 메시지를 지운다. 저장에 실패했는데 응답을 보내면 유실된다 → 저장 성공 후에만 응답(manual ack)
- **Paho 콜백 규칙**: 콜백 안에서 예외가 나가면 연결이 끊기고, 콜백 스레드에서 동기 호출(구독 등)을 하면 막힐 수 있다
- **ON CONFLICT DO NOTHING**: 중복 messageId를 DB가 걸러 준다. 영향받은 행 수(0/1)로 중복 여부를 안다
- **JPA 이름 규칙 함정**: `co2Ppm`, `tempC`처럼 숫자 뒤나 맨 끝의 대문자 한 글자는 밑줄로 나뉘지 않는다. `ddl-auto: validate`가 앱 시작 때 잡아 준다
- **Flyway 체크섬**: 주석만 바꿔도 체크섬이 달라진다. 커밋된 마이그레이션은 고치지 않고 새 버전을 추가한다
- **시간대**: DB(timestamptz)와 Hibernate를 UTC로 맞추면 서버가 어느 시간대에서 돌든 API 응답 시각이 같다. 화면에서 사용자 시간대로 바꿔 보여 준다
- **java.util.Random**: 시드가 가까우면 처음 값들이 거의 같다
- **React + Spring 한 주소**: Vite 빌드 결과를 Spring Boot 정적 리소스로 넣으면 CORS 없이 주소 하나로 서비스한다. 개발할 때는 Vite 프록시로 `/api`를 넘긴다

## 숫자 밑줄과 MQTT 통신 방식 (#50~#51)
- **숫자 밑줄 `30_000`**: 자릿수 구분자(Java 7+, TS/JS). 값은 30000. 쉼표는 값 구분자라 숫자 안에 못 쓴다. 숫자 사이에만 쓸 수 있다
- **MQTT vs 웹소켓**: 둘 다 연결 하나로 동시에 양방향. 웹소켓은 1:1 직통(전화), MQTT는 브로커 경유 발행/구독(단톡방)
  - MQTT는 받는 대상이 토픽 구독자 전체, 상대가 꺼져 있어도 세션이 있으면 브로커가 보관, QoS·keepalive·Last Will이 기본 기능
  - 패킷: CONNECT/CONNACK, PUBLISH/PUBACK, SUBSCRIBE/SUBACK, PINGREQ/PINGRESP, DISCONNECT
  - 우리 구조: 위로(측정값, #2) + 아래로(명령, #8)를 게이트웨이 연결 하나로. 화면은 HTTP 폴링

## #3 구현에서 배운 것
- **수동 확인 응답(manual ack)**: 처리가 끝난 뒤에만 PUBACK. MQTT는 확인 못 받은 메시지를 재연결 때만 다시 보내므로, 잠깐의 실패는 일부러 재연결한다
- **잠깐의 실패 vs 영구 실패**: 다시 하면 될 수 있는 것(DB 연결 실패)만 재시도, 다시 해도 같은 것(형식 오류, 무결성 위반)은 버린다. 구분을 잘못하면 같은 메시지가 끝없이 돌아온다(**poison message**)
- **Spring 예외 계층**: `TransientDataAccessException`(일시), `DataAccessResourceFailureException`(연결 실패), `DataIntegrityViolationException`(무결성 위반, 영구)
- **지수 백오프 + jitter**: 1초→2초→4초… 기준 최대 60초, ±30% 흔들기. 흔들지 않으면 모든 장비가 같은 순간에 몰린다
- **원형 버퍼**: 크기를 정해 두고 넘치면 가장 오래된 것부터 버린다. 보낸 뒤 PUBACK을 받아야 지운다
- **센서 고장값과 컬럼 크기**: 범위 밖 값도 저장하려면 컬럼이 그 값을 담을 수 있어야 한다. NUMERIC(4,1)은 999.9까지
- **테스트 격리**: 테스트가 로컬에서 실행 중인 브로커에 같은 클라이언트 ID로 붙으면 시연 서버를 끊는다. MQTT가 필요 없는 테스트는 끄고, 필요한 테스트는 ID를 매번 다르게
- **`OffsetDateTime.toString()` 함정**: 0초면 초를 생략한다(06:13Z). 비교할 때는 `ISO_OFFSET_DATE_TIME`으로 포맷한다
- **`@MockitoSpyBean`**: 실제 빈을 감싸서 특정 호출에만 장애를 끼워 넣는다
- **Awaitility `during()`**: "일정 시간 동안 계속 조건이 유지되는지"로 "일어나지 않음"을 확인한다

## #4 구현에서 배운 것
- **`@TransactionalEventListener(AFTER_COMMIT)`**: 트랜잭션이 커밋된 뒤에만 실행된다. 롤백되면 실행되지 않는다. 안에서 DB에 쓰려면 원래 트랜잭션이 끝났으므로 `REQUIRES_NEW`가 필요하다
- **기능 사이 의존 방향**: 측정값 기능은 "저장했다"는 이벤트만 발행하고, 이상 기능이 그걸 듣는다. 측정값 기능이 이상 기능을 몰라도 된다
- **히스테리시스**: 발생 기준(150Pa)과 해제 기준(130Pa)을 다르게 둬서, 기준값 근처에서 켜졌다 꺼졌다 반복하는 것을 막는다
- **부분 유니크 인덱스**: `WHERE status = 'OPEN'`인 행에만 유니크를 건다. 해결된 이상은 여러 개 남아도 되고, 열린 이상은 하나뿐
- **CHECK 제약으로 상태 규칙 지키기**: `(status = 'RESOLVED') = (resolved_at IS NOT NULL)`처럼 상태와 값이 어긋나는 행을 DB가 거부한다
- **규칙을 순수 클래스로**: 입력(최근 측정값) → 결과(발생/해제/그대로). DB 없이 단위 테스트로 경계값(150, 151, 130, 129)을 확인한다
- **저장된 최신 값으로 다시 판단**: 방금 받은 값이 아니라 DB의 측정 시각 최신 값으로 판단하면, 늦은 측정값이 순서 없이 와도 결과가 흔들리지 않는다
- **테스트 사이 간섭**: 같은 브로커를 쓰는 테스트 클래스끼리 앞 클래스의 구독이 뒤 클래스의 메시지를 가져갈 수 있다 → `@DirtiesContext(AFTER_CLASS)`로 클래스가 끝나면 앱을 닫는다

## #6 구현에서 배운 것
- **Last Will(유언 메시지)**: 연결할 때 브로커에 "내가 갑자기 끊기면 이걸 대신 보내 줘"라고 맡겨 둔다. 정상 종료(DISCONNECT)에는 나가지 않는다. 그래서 시뮬레이터는 정상 종료 때 offline을 직접 보낸다
- **retained 메시지**: 브로커가 토픽마다 마지막 하나를 보관했다가 새로 구독한 쪽에 바로 준다. 받는 쪽에서는 retain 플래그로 "지금 온 것"과 "보관하던 옛날 것"을 구분할 수 있다. 빈 메시지를 retained로 보내면 지워진다
- **half-open 연결**: Wi-Fi가 꺼져도 TCP 연결이 살아 있는 줄 아는 경우. keepalive가 끝날 때까지 Last Will이 안 나가므로 서버도 무수신 검사를 한다
- **비관적 잠금**: `@Lock(PESSIMISTIC_WRITE)` → `SELECT ... FOR UPDATE`. 먼저 잠근 트랜잭션이 끝날 때까지 다른 쪽은 기다린다. 잃어버린 갱신(lost update)을 막는다
- **트랜잭션 전파 정리**: `REQUIRED`(있으면 참여, 없으면 새로), `REQUIRES_NEW`(항상 새로, 커밋 후 리스너에서 필요), `MANDATORY`(반드시 이미 있는 트랜잭션 안에서, 없으면 예외 → "혼자 쓰면 안 되는 코드"를 표시)
- **같은 트랜잭션 이벤트 vs 커밋 후 이벤트**: 무엇이 더 중요한지에 따라 고른다. 측정값은 이상보다 중요해서 분리(#4), 연결 상태와 이상은 함께 움직여야 해서 묶음(#6)
- **`@Scheduled` + `@ConditionalOnProperty`**: 테스트에서는 스케줄러를 끄고 검사 메서드에 시각을 직접 넣어 30분을 기다리지 않는다
- **JSONB 매핑**: Hibernate 6에서는 `@JdbcTypeCode(SqlTypes.JSON)`만 붙이면 `List<String>`을 jsonb로 읽고 쓴다

## #5 구현에서 배운 것
- **"N분 지속" 판단**: 최신부터 거꾸로 이어진 구간을 찾는다. 시간은 측정 시각 기준. 측정값이 빈 구간은 끊긴 것으로 본다(이어 붙이면 옛날 값으로 지금 이상이 생김)
- **히스테리시스를 지속 시간에도**: CO2는 발생(1,000 초과 10분)과 해제(900 미만 10분)를 다르게. 기준값 근처에서 깜빡이지 않는다
- **심각도 올리기(escalation)**: 같은 이상을 새로 만들지 않고 심각도만 올린다. 내리지 않는 이유: 오르락내리락하면 보는 사람이 헷갈린다
- **테스트에서 시간 다루기**: 실제로 10분 기다리지 않고, 지속 시간 설정을 줄이고 측정 시각을 직접 넣는다. 늦은 측정값(2분)·시계 오차(5분) 기준 안쪽이면 "미래 측정 시각"으로 연속 데이터를 만들 수 있다
- **테스트 데이터 격리**: 테스트끼리 같은 DB를 쓰면 한 테스트가 남긴 데이터(특히 미래 시각)가 다른 테스트의 "최신 값"을 바꾼다. 전용 데이터를 쓰거나 끝나면 지운다
- **시뮬레이터도 검증 대상**: 규칙이 맞아도 시나리오 데이터가 기준 근처를 맴돌면 해제가 안 된다. 실제 장비 데이터에서도 같은 일이 생길 수 있다(기준 근처 노이즈)
- **`BigDecimal` 올림**: `setScale(0, RoundingMode.CEILING)`. 실수 계산(double)으로 하면 148.5가 148.49999…가 될 수 있다
- **iCloud 동기화 폴더**: 지운 파일이 되살아날 수 있다. 빌드 전 `git status`로 모르는 파일을 확인한다

## #7 구현에서 배운 것
- **안전 제어는 현장, 서버는 감시**: 후드 연동을 서버가 하면 인터넷이 끊길 때 실내 압력이 깨진다. 서버는 "연동이 실제로 일어났는지"를 이벤트와 측정값으로 나중에 확인한다(ADR-0001)
- **이벤트와 측정값의 시간 맞추기**: 이벤트(일어난 시각)와 측정값(측정 시각)을 둘 다 장비 시각으로 비교한다. 받은 순서는 상관없다
- **확인을 미루는 설계**: 60초 뒤 측정값이 와야 확인할 수 있으므로, 받을 때 확인하지 않고 저장해 두고 주기 검사로 확인한다. "확인 전" 상태를 행에 두면(null) 부분 인덱스로 빨리 찾는다
- **확인 보류도 결과다**: 판단할 수 없는 경우(데이터 없음, 너무 짧은 사용)를 "무반응"으로 몰면 오탐이 된다. 세 번째 결과를 둔다
- **고장 확인은 늦은 데이터도 쓴다**: 지금 상태 규칙(#5)과 반대. 고장은 시간이 지나도 의미가 남는다
- **실패 모드를 구체적으로**: VEMC 고장 = "후드는 감지하지만 환기장치로 신호가 안 감"(배선 불량). 그래야 서버가 감지할 수 있는 형태가 된다

## #13 구현에서 배운 것
- **MQTT 인증과 인가**: 인증(누구냐: 계정·비밀번호, 인증서)과 인가(무엇을 할 수 있냐: 토픽 ACL)는 다르다. 브로커 ACL은 토픽 단위라 "장비 신원은 토픽에서 읽는다"(스펙 4.3)와 맞물린다
- **최소 권한**: 게이트웨이에 `jabjaje/1/#` 전체를 주지 않고 쓰기·읽기 토픽을 나눴다. 명령은 서버만 보낸다
- **MQTT 5 거부 응답**: 권한 없는 발행은 연결을 끊지 않고 PUBACK 이유 코드 0x87(135, Not authorized)로 돌려준다. MQTT 3.1.1은 거부를 알릴 방법이 없어 조용히 버린다
- **클라이언트 ID 탈취**: 같은 클라이언트 ID가 접속하면 브로커가 먼저 붙은 쪽을 끊는다(session takeover). `use_username_as_clientid`로 계정과 ID를 묶는다
- **비밀은 저장소 밖**: 해시도 올리지 않는다. 시작할 때 환경변수로 만든다. 운영은 비밀 관리 서비스와 장비별 인증서(mTLS)
- **설정 파일도 테스트한다**: 저장소의 실제 브로커 설정으로 컨테이너를 띄워 권한을 확인했다. 설정이 바뀌면 테스트가 잡는다

## #8 구현에서 배운 것
- **명령 저장과 발행 순서**: 저장 커밋 → 발행. 반대로 하면 저장 실패 시 장비만 명령을 안다. 발행이 실패하면 "보냄"으로 남고 재시도(#9)가 처리한다. 완전히 묶으려면 아웃박스 패턴(명령 테이블을 발행 대기열로 쓰고 별도 발행기가 보냄)을 쓴다
- **retained 금지(command)**: 재연결 때 브로커가 옛 명령을 다시 주면 몇 시간 뒤 부스트가 켜진다
- **잘못된 요청과 거절의 구분**: 요청 자체가 틀리면 400(기록 안 함), 요청은 맞는데 지금 보낼 수 없으면 기록(REJECTED_OFFLINE), 장비가 거절하면 사유와 함께 기록(REJECTED)
- **장비 우선순위**: 자기 보호(동결 방지) > 현장 연동(후드) > 원격 명령. 서버가 아니라 장비가 판단한다
- **자동 복귀**: 해제 명령을 보내지 않아도 지속시간이 지나면 장비가 스스로 돌아온다. 해제 명령이 유실돼도 안전하다
- **필드 추가만(ADR-0004)**: 측정값에 `boost`를 더할 때 없으면 false로 본다. 예전 게이트웨이가 섞여 있어도 깨지지 않는다

## #9 구현에서 배운 것
- **최소 한 번 전달 + 멱등 처리**: 재시도로 같은 명령이 두 번 와도 장비가 commandId를 기억해 한 번만 적용하고 같은 결과를 다시 응답한다
- **원하는 상태(desired state)**: 명령을 "실행할 동작"이 아니라 "원하는 상태"로 보면, 몰려온 명령 중 최신 하나만 의미가 있다. 서버도 장비당 대기 명령은 하나(밀려남)
- **만료는 두 겹**: 브로커의 MQTT 5 메시지 만료(만료된 메시지는 넘기지 않음) + 장비의 expiresAt 검사(만료 기능이 없는 브로커 대비). 재시도는 만료를 늘리지 않는다
- **세션 유지(persistent session)가 있어야 오프라인 큐가 생긴다**: clean start면 끊긴 동안의 QoS 1 메시지를 브로커가 버린다. 반대로 세션을 유지하면 오래된 명령이 몰려오므로 만료와 최신 하나만 규칙이 같이 필요하다
- **늦은 응답도 정보다**: 시간 초과 뒤 온 응답을 버리지 않고 실제 결과로 기록하면, 화면에 "늦게 적용됨"으로 사실대로 보여 줄 수 있다
- **조용한 끊김(half-open)**: Last Will이 안 나가는 끊김은 서버가 무수신 검사 전까지 모른다. 그 사이 보낸 명령이 이 티켓의 핵심 시나리오다
- **디바이스 섀도와의 관계**: 장비가 많아지면 서버는 desired만 저장하고 장비는 reported를 보고하는 섀도 방식으로 간다. 지금 구조(최신 하나, 만료)가 그 작은 버전이다

## #10 구현에서 배운 것
- **숫자는 코드, 해석은 AI**: 7일치 측정값 2만 개를 그대로 보내지 않고 DB에서 평균·개수만 집계해 지표 10개로 줄인다. AI가 계산을 틀릴 일이 없고 입력이 작아 비용·지연도 준다
- **근거 이름을 목록으로 묶기**: 상황 요약의 지표 이름 집합(`METRIC_KEYS`)을 검증에도 그대로 쓴다. AI가 "습도 추세" 같은 없는 근거를 대면 코드가 잡는다(지어낸 근거, hallucination)
- **출력 검증이 프롬프트보다 확실하다**: "무상 교체 약속하지 마"라고 써도 모델이 지킨다는 보장은 없다. 금액·무상·보증 표현을 코드로 거르고, 걸리면 사람에게 넘긴다(프롬프트 인젝션 대응의 마지막 단계)
- **느린 외부 호출 중에는 DB 트랜잭션을 열지 않는다**: AI 호출이 10초 걸리면 그동안 DB 연결 하나를 붙잡는다. 맡기 → (트랜잭션 없이) AI 호출 → 짧은 트랜잭션으로 저장
- **한 줄 UPDATE로 일 맡기(claim)**: `UPDATE ... WHERE status = 'RECEIVED' AND (started_at IS NULL OR started_at < 오래전)` 결과가 1인 쪽만 처리한다. 접수 직후 처리와 재처리 스케줄러가 겹쳐도 한 번만 돈다. 서버가 도중에 꺼지면 "오래전"이 지나 다시 맡는다
- **@Async + AFTER_COMMIT**: 커밋 뒤에 별도 스레드에서 돌려 고객 응답이 AI를 기다리지 않는다. 대기열이 가득 차면 버리고 스케줄러가 줍는다(유실 없는 이유는 DB의 접수됨 상태가 할 일 목록 역할을 하기 때문)
- **인터페이스 + 가짜 구현**: 외부 API 없이도 시연·테스트가 끝까지 돈다. 가짜 구현이 "일부러 틀린 응답"을 낼 수 있어야 검증·재시도·사람 확인 필요 경로를 테스트할 수 있다

## #11 구현에서 배운 것
- **AI는 초안, 사람이 확정**: 고객 안내는 판정이 있어야만 나간다. 고객용 조회는 판정 전에는 안내문이 비어 있고, AI 초안은 직원 화면에만 있다(ADR-0005). "AI가 고객에게 직접 답하지 않는다"를 API 구조로 강제한 것
- **"고쳤는지"는 서버가 정한다**: 화면의 표시를 믿지 않고 제출 내용과 AI 소견을 항목별로 비교한다. 고친 항목(`edited_fields`)이 쌓이면 AI가 어디서 자주 틀리는지(예: 고객 안내문, 권하는 점검) 볼 수 있다. 사람의 수정이 곧 평가 데이터
- **같은 구조로 저장하면 비교가 쉽다**: 판정을 AI 소견과 같은 항목으로 나눠 두어 비교 코드가 단순하다
- **상태 전이 지키기**: 판정은 소견 완료·사람 확인 필요에서만. 접수됨(AI 처리 중)이나 판정됨이면 409. 엔티티 메서드가 한 번 더 막는다
- **동시 판정**: 신청 행을 잠가 한 줄로 세우고, 유니크 제약을 두 번째 안전장치로. 백그라운드 AI 처리는 "접수됨일 때만" 상태를 바꾸므로 판정됨을 덮어쓰지 않는다
- **직원 안내문은 검사 규칙이 다르다**: AI 안내문은 금액·무상 표현을 막지만 직원은 보증 수리처럼 실제로 약속해야 할 때가 있다. 검사는 "누가 쓴 글인가"에 따라 달라진다

## #12 구현에서 배운 것
- **구조화 출력(structured outputs)**: JSON 스키마를 API에 함께 보내면 그 형식의 JSON만 생성된다. 형식은 API가, 의미(값이 있는 근거, 금지 표현)는 우리 검증기가 본다. 두 겹이다
- **스키마는 고정**: 요청마다 스키마가 바뀌면 API가 준비 작업을 매번 다시 한다. Java `Map.of`는 꺼내는 순서가 실행마다 달라질 수 있어 `LinkedHashMap`으로 키 순서를 고정했다
- **채점하기 쉬운 출력을 설계한다**: 원인 제목(자유 문장) 대신 분류(정해진 8가지)를 같이 받으면 평가가 "값이 같은가" 한 줄이 된다. 채점용 AI가 필요 없고 결과가 흔들리지 않는다
- **고정 평가 세트**: 같은 입력으로 모델·프롬프트·effort를 바꿔 가며 정답률·시간·비용을 비교한다. 예시(few-shot)가 평가 시나리오와 비슷하면 점수가 부풀어 오르는 "평가 누설"이 생긴다
- **모델 라우팅 네 가지**: 규칙 기반, 분류 모델 라우터, 단계적 승격(싼 모델 먼저, 실패하면 강한 모델), 같은 모델의 effort만 조절. 우리는 이미 검증기와 재시도가 있어 단계적 승격이 자연스럽다. 단, 검증은 통과했지만 원인이 틀린 소견은 승격되지 않는다
- **200 응답도 실패일 수 있다**: 안전 거절(`refusal`), 길이 한도(`max_tokens`)는 HTTP는 성공인데 쓸 수 없는 응답이다. `stop_reason`을 먼저 본다
- **시간 제한은 겹으로 계산한다**: SDK 시간 제한 × (재시도 + 1) = 시도 한 번 최대 시간, 그 × 시도 수 < 재처리 기준. 앱이 시작할 때 검사해서 설정 실수를 바로 잡는다
- **비밀값**: 키는 환경변수로만, `.env`는 `.gitignore`, 테스트는 키가 있어도 가짜 AI 강제(실수로 비용이 나가지 않게), 로그에 키가 찍히지 않는지 확인
- **가짜 HTTP 서버(MockWebServer)**: 실제 API 대신 응답을 꾸며서 시간 초과·거절·잘림·요청 내용을 비용 없이 시험한다

## #14 구현에서 배운 것
- **운영값과 시연값 나누기**: 운영 기본값은 그대로 두고 Compose 덮어쓰기 파일(`-f docker-compose.demo.yml`)로 짧은 기준 시간을 켠다. 비밀값이 없어서 저장소에 올려도 된다
- **시연 경로도 자동 점검한다**: 손으로 5단계를 다 해 보면 15분이 넘는다. 점검 스크립트가 ✓/✗로 몇 분 안에 알려 주면 면접 직전에도 안심하고 확인할 수 있다
- **점검이 틀릴 수도 있다**: 첫 점검에서 "늦은 측정값이 없다"고 실패했는데, 실제로는 75초만 끊겨 2분 기준에 못 미쳤을 뿐 데이터는 다 채워져 있었다. 실패하면 먼저 DB를 직접 보고, 기능이 틀렸는지 점검 기준이 틀렸는지 가린다
- **재현과 실제를 구분해 적는다**: 검증기 사례는 가짜 AI로 재현한 것이라고 README에 분명히 적었다. 면접에서 "실제 AI가 그렇게 틀렸나"를 물으면 정직하게 답할 수 있다

- **비용은 먼저 작게 재고 늘린다**: 평가 15회를 바로 돌리기 전에 5회(시나리오마다 1번)만 돌려 실제 토큰으로 비용을 쟀다($0.08). 그걸로 세 구성 합계를 추정하고 나서 본 평가를 돌렸다. 하루 전체 비용은 약 $0.57
- **effort는 출력(생각) 토큰을 줄인다**: Opus low는 medium보다 출력이 약 30% 적어 더 빠르고 싸면서 정답률은 같았다. 하지만 시나리오 5개로는 품질을 내릴 근거가 부족해 기본값은 그대로 뒀다
- **같은 평가도 다시 돌리면 흔들린다**: Haiku는 같은 구성인데 14/15와 12/15가 나왔다. 한 번 돌린 점수만 믿지 않고 반복해서 본다. 실행기가 같은 이름 보고서를 덮어써서, 이제는 `-2`를 붙여 둘 다 남긴다
- **검증기는 형식을 잡고, 판단은 평가 세트가 잡는다**: Haiku의 틀린 답도 형식·근거·부품이 맞아 검증을 통과했다. 그래서 "검증 실패하면 강한 모델로 승격"은 판단 실수를 못 고친다. 이게 기본 모델을 Opus로 둔 이유다
- **기록이 없으면 단정하지 않는다**: Haiku 1회차의 재시도 1건은 이유가 남지 않았다. 그래서 "금지 표현이 한 번도 안 걸렸다"고 쓰지 않았다. 대신 실행기가 재시도한 실행의 오류도 남기게 고쳤다

## #15 복기 중 정리: MQTT, HTTP, 웹소켓, Kafka
- **MQTT 정의**: TCP 위에서 도는 가벼운 발행/구독(publish/subscribe) 메시지 프로토콜. 모두가 브로커에만 연결하고, 보내는 쪽은 토픽에 발행, 받는 쪽은 토픽을 구독한다. 보내는 쪽과 받는 쪽은 서로 주소를 모른다 [일반]
- **HTTP와의 차이**: HTTP는 클라이언트가 요청해야만 서버가 답한다(요청-응답, 주로 짧은 연결). MQTT는 장비가 먼저 연결을 열어 두고 그 연결로 양쪽이 아무 때나 보낸다. 그래서 공유기 뒤 게이트웨이에도 서버가 명령을 밀어 줄 수 있다
- **웹소켓을 안 쓰는 이유**: 웹소켓도 연결 하나로 양방향이지만 "선로"만 준다. 누구에게 보낼지(장비별 연결 관리), 받았는지 확인·재전송(QoS), 끊긴 동안 보관(세션), 갑작스러운 끊김 알림(Last Will), 오래된 명령 버리기(만료)를 전부 직접 만들어야 한다. MQTT는 이것이 프로토콜과 브로커에 들어 있다. 웹소켓은 브라우저 실시간 화면에 맞다(MQTT over WebSocket도 있다)
- **Kafka 정의**: 메시지를 디스크에 순서대로 쌓는 로그(append-only)로 오래 보관하고, 소비자마다 읽은 위치(offset)를 따로 관리하는 분산 이벤트 스트리밍 플랫폼. 다시 읽기(replay), 파티션으로 수평 확장, 높은 처리량이 강점 [일반]
- **Kafka를 장비에 직접 안 붙이는 이유**: 클라이언트가 무겁고, 수천~수십만 장비 연결과 약한 네트워크·Last Will 같은 장비 쪽 기능을 전제로 만든 게 아니다. 현업은 보통 장비 → MQTT 브로커 → Kafka → 서버들로 역할을 나눈다
- **우리 MVP가 Kafka 없이 데이터를 지키는 방법**: QoS 1 + 저장 성공 후에만 PUBACK(manual ack, ADR-0012) + messageId 중복 거름(ON CONFLICT). 서버 안 비동기 처리는 DB 상태가 할 일 목록 역할(ADR-0015). Kafka는 ADR-0013·0015에서 "규모가 커지면 다시 검토"로 기각했다
- **게이트웨이에 서버를 배포하나?**: 아니다. 게이트웨이에는 연결을 "거는" 프로그램(MQTT 클라이언트)이 돈다. 연결을 "기다리는" 서버는 브로커뿐(1883 포트). Spring 서버도 브로커 입장에선 MQTT 클라이언트다(HTTP로는 8080에서 기다리는 서버). 거는 쪽이라 공유기 포트를 열 필요가 없다
- **IoT가 연결되는 세 구간**: ① 장비 ↔ 게이트웨이: 현장 배선·근거리 통신(접점, RS-485/Modbus, BLE, Zigbee 등, 잡자재 실제 방식은 확인 필요) ② 게이트웨이 ↔ 인터넷: 고객 Wi-Fi·유선·LTE ③ 인터넷 위: TCP/IP → (운영은 TLS) → MQTT → 브로커. 설치할 때 기기에 ID·비밀번호·브로커 주소를 넣어 둔다(우리: `gw-s1`, ACL 계정). Wi-Fi 칩이 있는 장비는 게이트웨이 없이 직접 붙기도 한다 [일반]
- **Last Will과 무수신 검사를 둘 다 쓰는 이유**: Last Will은 브로커가 끊김을 알아챌 때만 나간다. 프로그램이 죽으면(OS가 연결을 닫음) 바로, 전원·Wi-Fi가 꺼지면(half-open) keepalive 30초의 1.5배인 약 45초 뒤, 연결은 살아 있는데 데이터만 안 오면 영영 안 나간다. 무수신 검사는 "마지막으로 받은 지 2분"만 보므로 느리지만 모든 경우를 잡는다. 빠른 알림 + 안전망. 그래서 끊긴 시각은 Last Will 도착 시각이 아니라 마지막 수신 시각(`disconnectedAt = lastReceivedAt`)
- **리스너와 스케줄러 (#15 복기)**: 서비스를 깨우는 입구는 셋이다. HTTP 컨트롤러(사람이 요청), MQTT 리스너(장비가 메시지를 보냄, 4개), 스케줄러(시계가 깨움, 4개). 서비스가 끝나면 이벤트를 내고, 다른 기능의 이벤트 리스너(7개)가 이어서 처리한다
  - **이벤트 리스너를 쓰는 이유**: 기능끼리 서로 몰라도 되게. 측정값 기능은 "저장했다"만 알리고, 이상·게이트웨이 기능이 각자 듣는다
  - **커밋 후(4개) vs 같은 트랜잭션(3개)**: "후속 처리가 실패하면 본 처리도 취소돼야 하나?"로 고른다. 측정값은 이상 평가보다 중요해서 커밋 후, 게이트웨이 오프라인 상태와 오프라인 이상은 함께여야 해서 같은 트랜잭션(ADR-0013·0014). 명령 발행도 커밋 후(저장이 롤백됐는데 장비만 명령을 아는 일을 막음)
  - **스케줄러가 필요한 이유**: "일어나지 않은 일"에는 이벤트가 없다. 메시지가 안 옴(무수신 30초), 응답이 안 옴(명령 재시도·시간 초과 2초), 시간이 지나야 판단 가능(후드 ON 60초 뒤 급기, 30초), 유실된 일 줍기(접수된 채 남은 A/S 60초)
  - **스케줄러에는 로직이 없다**: 서비스 하나만 부른다. 테스트에서는 끄고(`check-enabled=false`) 시각을 넣어 서비스를 직접 불러 30분을 기다리지 않는다. `fixedDelay`라 앞 실행이 끝난 뒤부터 다음 간격을 센다(겹치지 않음)
- **Paho (#15 복기)**: Eclipse 재단의 오픈소스 MQTT 클라이언트 라이브러리. JDBC 드라이버가 DB 프로토콜을 대신 다뤄 주듯, CONNECT·PUBLISH·PUBACK·SUBSCRIBE·PINGREQ 같은 MQTT 패킷을 대신 만들고 받아 준다. 우리는 `org.eclipse.paho.mqttv5.client:1.2.5`(MQTT 5)를 서버와 시뮬레이터 모두 직접 쓴다(ADR-0009, Spring Integration MQTT는 기각)
  - 쓰는 곳: `MqttClientManager`(서버 연결·구독·수신·manual ack·발행), `RemoteCommandSender`(명령 발행, 만료 설정), `GatewaySimulator`(Last Will·직접 재접속·버퍼 발행)
  - 함정 네 가지: ① 기본은 자동 PUBACK → `setManualAcks(true)` ② 콜백 밖으로 예외가 나가면 연결이 끊김 → 모든 예외를 잡음 ③ 콜백 스레드에서 동기 호출(구독)하면 막힐 수 있음 → 다른 스레드로 ④ 자동 재연결 간격이 최대 2분 → 서버는 30초로 줄이고, 시뮬레이터는 jitter가 없어 끄고 직접 재접속
