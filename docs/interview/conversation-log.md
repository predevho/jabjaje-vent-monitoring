## 2026-10-23 (금) — 공고 분석부터 설계 확정까지

### #1 공고 분석
- **내가 한 말**: 사람인 공고(잡자재 백엔드/IoT 플랫폼 개발자) 이미지 2장과 링크를 주고, IoT & BEMS 시스템인지 모르겠고 기술 스택도 안 나와 있으니 확인하고 AI 업무를 같이 생각해보자고 했다.
- **결론**
  - 잡자재는 BEMS 전문 회사가 아니라, 패시브하우스용 열회수 환기장치(KOMFOVENT)·복사냉방·기밀자재 유통사가 IoT 플랫폼으로 확장하려는 단계로 보인다. 직원 11명, 2025년 매출 약 36.7억.
  - IoT의 씨앗은 자체 컨트롤러 **VEMC**(후드가 켜지면 환기장치 급기↑ 배기↓).
  - 기술 스택이 없는 이유: 개발팀이 없어서 들어간 사람이 정하게 될 가능성이 크다. AI로 1인 완주 가능한 사람을 찾는 공고.
  - 사이드프로젝트 방향: 환기 모니터링 MVP + A/S 1차 진단 AI.

### #2 기술 스택 선택
- **내가 한 말**: 아는 기술로 할지, Node나 Python으로 할지 물었다.
- **결론**: 아는 스택을 추천. 공고가 "AI 코드를 직접 검증·디버깅"하는 능력을 보기 때문에, 설명할 수 있는 스택이 유리하다.

### #3~#4 스택 확정
- **내가 한 말**: 면접은 다음 주 화요일(10/27). Java Spring으로 하자. Java 17, Spring Boot 3.x로 하고 PostgreSQL은 유지, 나머지는 상황 보고 트레이드오프로 정하겠다. 이유는 현업에서 많이 쓰이고 21 이상은 필요한 기능을 안 쓸 것 같아 오버스펙이 우려되어서.
- **결론**: Java 17, Spring Boot 3.5.x, PostgreSQL 확정. 범위는 A안(데이터 흐름 전체 + A/S 진단 AI). 면접 포인트: "가상 스레드는 장비 수천 대 규모에서 검토".

### #5 MQTT란
- **내가 한 말**: MQTT가 뭐냐고 물었다.
- **결론**: 브로커를 가운데 둔 발행/구독 방식의 가벼운 IoT 통신. 장비가 먼저 연결하므로 공유기 뒤 장비에도 명령을 보낼 수 있다. QoS, Last Will. 실제 장비는 Modbus를 쓰고 게이트웨이가 MQTT로 올리는 구조가 일반적.

### #6~#7 데이터 구조와 ERD
- **내가 한 말**: 다음으로 진행하자. 테이블을 글로만 보니 연결이 안 보이니 ERD로 보여달라.
- **결론**: 테이블 8개(site, device, telemetry, device_event, alert, command, as_ticket, diagnosis) ERD 확인. 중복 메시지 처리(messageId 유니크), 측정 시각과 수신 시각 분리, AI 입력 사본 저장.

### #8 알림 규칙과 VEMC 흐름
- **내가 한 말**: 다음으로 진행해달라.
- **결론**: 알림 규칙 6개(CO2, 필터, 풍량, 바이패스, 오프라인, VEMC 무반응). VEMC를 서버가 제어하면 인터넷 장애 때 멈추므로 **현장 연동 + 서버 감시**로 변경.

### #9 인터넷이 끊기면
- **내가 한 말**: 인터넷이 끊어지는데 어떻게 IoT 통신이 가능하냐고 물었다.
- **결론**: 현장 연동은 전선 신호라 인터넷이 필요 없다. 인터넷은 보고·원격 제어에만 쓴다. 끊긴 동안 게이트웨이가 데이터를 쌓아두고, 복구 후 보낸다.

### #10 OSI 7계층과 AI 진단 설계
- **내가 한 말**: 넘어가자, OSI 7계층도 같이 공부하게 생겼다.
- **결론**: OSI 계층과 프로젝트 대응 정리. AI 진단 설계: 숫자 계산은 코드, AI는 해석만, 결과를 코드로 검증, 직원 승인 후 고객 안내.

### #11 스펙 작성과 현장 리스크 검토
- **내가 한 말**: 스펙으로 정리하고, 기술 문제점·해결방안·위험성·통신 안정성 등 현장 관점으로 다시 검토해달라.
- **결론**: 리스크 39개 검토, 30개 반영, 9개 문서화. 핵심: 명령 만료·멱등성·자동 복귀, 오프라인 알림 2단계, 늦은 데이터 처리, 브로커 ACL, 급·배기 함께 부스트, 프롬프트 인젝션 대응.

### #12 오프라인 표시와 명령 몰림
- **내가 한 말**: Wi-Fi 오프라인인데 알림이 안 오면 어떻게 표시하는지, 쌓인 명령이 나중에 한꺼번에 몰리면 어떻게 처리하는지 물었다. AI 스킬은 mattpocock 스킬을 참고해서 진행하자고 했다.
- **결론**
  - 오프라인: 화면에는 2분부터 표시, 직원 알림은 30분부터. 고객에게는 "환기장치는 집 안에서 계속 동작 중"이라고 안내.
  - 명령 몰림: 장비당 대기 명령 1개, 브로커 메시지 만료, 장비는 최신 명령 하나만 적용, 늦은 응답 반영. 확장 방향은 디바이스 섀도.
  - mattpocock 스킬: grill-with-docs(용어집·ADR), teach, wait-what, to-tickets, tdd/implement 흐름으로 진행.

### #13~#14 플러그인 설치

- **결론**: 설치 완료. 직접 입력하는 스킬(`/setup-matt-pocock-skills` 등)은 입력해서 동작을 확인한다.

### #15 하드웨어 업데이트
- **내가 한 말**: 기능이 바뀌면 하드웨어도 업데이트해야 하는지, 앱만 업데이트하면 되는지 물었다.
- **결론**: 변경 위치에 따라 다르다. 판단 로직은 서버에 둬서 대부분 서버 배포로 끝낸다. 게이트웨이는 버전·지원 기능을 보고하고, 메시지는 필드 추가만 허용해서 구버전과 공존한다(스펙 4.4).
