## 2026-10-23 (금) — 공고 분석부터 설계 확정까지

### #1 공고 분석
- **내가 한 말**: 사람인 공고(잡자재 백엔드/IoT 플랫폼 개발자) 이미지 2장과 링크를 주고, IoT & BEMS 시스템인지 모르겠고 기술 스택도 안 나와 있으니 확인하고 AI 업무를 같이 생각해보자고 했다.
- **결론**
  - 잡자재는 BEMS 전문 회사가 아니라, 패시브하우스용 열회수 환기장치(KOMFOVENT)·복사냉방·기밀자재 유통사가 IoT 플랫폼으로 확장하려는 단계로 보인다. 직원 11명, 2025년 매출 약 36.7억.
  - IoT의 씨앗은 자체 컨트롤러 **VEMC**(후드가 켜지면 환기장치 급기↑ 배기↓).
  - 기술 스택이 없는 이유: 개발팀이 없어서 들어간 사람이 정하게 될 가능성이 크다. AI로 1인 완주 가능한 사람을 찾는 공고.
  - 사이드프로젝트 방향: 환기 모니터링 MVP + A/S 1차 진단 AI.

### #2 기술 스택 선택
- **내가 한 말**: 아는 기술로 할지, Node나 Python으로 할지 물었다.
- **결론**: 아는 스택을 추천. 공고가 "AI 코드를 직접 검증·디버깅"하는 능력을 보기 때문에, 설명할 수 있는 스택이 유리하다.

### #3~#4 스택 확정
- **내가 한 말**: 면접은 다음 주 화요일(10/27). Java Spring으로 하자. Java 17, Spring Boot 3.x로 하고 PostgreSQL은 유지, 나머지는 상황 보고 트레이드오프로 정하겠다. 이유는 현업에서 많이 쓰이고 21 이상은 필요한 기능을 안 쓸 것 같아 오버스펙이 우려되어서.
- **결론**: Java 17, Spring Boot 3.5.x, PostgreSQL 확정. 범위는 A안(데이터 흐름 전체 + A/S 진단 AI). 면접 포인트: "가상 스레드는 장비 수천 대 규모에서 검토".

### #5 MQTT란
- **내가 한 말**: MQTT가 뭐냐고 물었다.
- **결론**: 브로커를 가운데 둔 발행/구독 방식의 가벼운 IoT 통신. 장비가 먼저 연결하므로 공유기 뒤 장비에도 명령을 보낼 수 있다. QoS, Last Will. 실제 장비는 Modbus를 쓰고 게이트웨이가 MQTT로 올리는 구조가 일반적.

### #6~#7 데이터 구조와 ERD
- **내가 한 말**: 다음으로 진행하자. 테이블을 글로만 보니 연결이 안 보이니 ERD로 보여달라.
- **결론**: 테이블 8개(site, device, telemetry, device_event, alert, command, as_ticket, diagnosis) ERD 확인. 중복 메시지 처리(messageId 유니크), 측정 시각과 수신 시각 분리, AI 입력 사본 저장.

### #8 알림 규칙과 VEMC 흐름
- **내가 한 말**: 다음으로 진행해달라.
- **결론**: 알림 규칙 6개(CO2, 필터, 풍량, 바이패스, 오프라인, VEMC 무반응). VEMC를 서버가 제어하면 인터넷 장애 때 멈추므로 **현장 연동 + 서버 감시**로 변경.

### #9 인터넷이 끊기면
- **내가 한 말**: 인터넷이 끊어지는데 어떻게 IoT 통신이 가능하냐고 물었다.
- **결론**: 현장 연동은 전선 신호라 인터넷이 필요 없다. 인터넷은 보고·원격 제어에만 쓴다. 끊긴 동안 게이트웨이가 데이터를 쌓아두고, 복구 후 보낸다.

### #10 OSI 7계층과 AI 진단 설계
- **내가 한 말**: 넘어가자, OSI 7계층도 같이 공부하게 생겼다.
- **결론**: OSI 계층과 프로젝트 대응 정리. AI 진단 설계: 숫자 계산은 코드, AI는 해석만, 결과를 코드로 검증, 직원 승인 후 고객 안내.

### #23~#27 용어집과 ADR (`/grill-with-docs`)
- **내가 한 말**
  - 애매한 부분이 무슨 뜻인지 모르겠다. 용어 의미가 중복돼서 묻는 거냐고 물었다.
  - 하나로 정하면 나머지 기능이 빠지는 거냐고 물었다.
  - 용어 내용이 비슷하면 오히려 헷갈릴 것 같다. 예를 들어 문제 상태는 "접수", 사람에게 보내는 건 "알림"처럼 하면 어떠냐, 선택지를 나열해 달라고 했다.
  - 추천대로 진행하자고 했다.
- **결론**
  - 묻는 이유는 세 가지다. 같은 대상에 이름이 여러 개, 한 단어에 뜻이 두 개, 용어 때문에 동작이 틀어지는 경우(게이트웨이를 장비로 묶어 환기장치가 "오프라인"으로 보이던 문제).
  - 이름을 정해도 기능은 빠지지 않는다. 뜻이 두 개면 둘 다 남기고 이름만 따로 붙인다.
  - "접수"는 A/S 접수와 겹쳐서 쓰지 않았다. "사람에게 보내는 것 = 알림"은 일상어와 같아서 채택했다.
  - 확정 용어: 현장, 장비(게이트웨이 제외), 확인 불가, 일시 끊김 / 오프라인, 후드 연동 / 부스트, 최소 환기량 / 목표 풍량, 이상 / 알림, A/S 신청, AI 소견 / 판정
  - 치환하다가 새 충돌을 발견했다. "이상"은 "30분 이상"처럼 숫자 기준에도 쓰인다. 숫자에는 "넘게", "≥"를 쓰기로 했다.
  - `GLOSSARY.md`, ADR 6건(`docs/adr/0001~0006`) 작성, 스펙 v4로 이름 정리

### #28 게이트웨이는 몇 계층인가
- **내가 한 말**: 게이트웨이가 물리적 전송계층인지 네트워크 전송계층인지, 스펙에서 무엇이 바뀐 건지 헷갈린다고 했다.
- **결론**: 게이트웨이는 계층이 아니라 기기다. 집 안쪽은 Modbus/RS-485, 바깥쪽은 MQTT/TCP/IP로 여러 계층에 걸쳐 일하고, 7계층에서 프로토콜을 바꾸는 응용 계층 게이트웨이다. 스펙에서 바뀐 건 물리 구조가 아니라 데이터 분류다. 게이트웨이를 "장비"에서 "연결 통로"로 분리했다.

### #59 #6 결정 중: Redis + Lua로 원자적으로 처리하면?
- **내가 한 말**: Q5(오프라인 상태와 이상을 함께 바꾸기)를 Redis에 두고 Lua 스크립트로 원자적으로 처리하는 건 오버스펙인지 물었다.
- **결론**: 이 MVP에는 오버스펙이다.
  - 바꿀 값(게이트웨이 상태, 이상 행)이 둘 다 PostgreSQL에 있다. DB 트랜잭션 하나면 이미 원자적이다
  - Redis를 넣으면 Redis와 PostgreSQL 두 곳에 쓰게 된다. Lua는 Redis 안에서만 원자적이라, 둘 중 하나만 성공하는 문제(dual write)가 새로 생긴다
  - 경쟁 문제(Q4)도 행 잠금이면 서버가 여러 대여도 DB가 막아 준다
  - Redis가 맞는 때: 장비가 수만 대라 측정값마다 `last_received_at`을 DB에 쓰는 게 부담일 때. 마지막 수신 시각만 Redis Sorted Set(점수 = 수신 시각)에 두고 `ZRANGEBYSCORE`로 2분 넘은 것만 찾은 뒤, 상태가 바뀔 때만 DB에 쓴다. 이때 "찾고 표시하기"를 Lua로 한 번에 한다
  - ADR-0014의 검토한 대안에 기록하기로 함

### #60 #6 게이트웨이 연결 상태와 오프라인 이상
- **내가 한 말**: 결정 7가지를 추천대로 적용하라고 했다. 앞으로 답변은 영어 없이 무조건 한국어로 써 달라고 했다(읽을 수는 있지만 시간이 오래 걸린다).
- **결론**
  - 새 기능 패키지 `vent/gateway/`(엔티티 이동), 시간 입구인 `scheduler/` 레이어 추가
  - 수신으로 보는 것: 측정값 저장(커밋 후 이벤트), retained가 아닌 online. 다시 구독할 때 오는 옛날 retained online은 버전·지원 기능만 기록. offline은 retained여도 반영
  - 끊긴 시각은 마지막 수신 시각(Last Will은 실제보다 약 45초 늦게 온다)
  - 동시 수정: MQTT 스레드와 스케줄러 스레드가 같은 행을 바꾸므로 행 잠금(`SELECT ... FOR UPDATE`)
  - 오프라인 이상은 상태 변경과 같은 트랜잭션(`@EventListener` + `MANDATORY`). #4(커밋 후, 새 트랜잭션)와 반대로 정한 이유를 ADR-0014에 기록
  - 시뮬레이터: 연결할 때 online(retained, 버전 1.0.0, BOOST·HOOD_EVENT), Last Will offline. 시나리오 `network-down`(DISCONNECT 없이 소켓만 끊어 Last Will 유도), `network-up`
  - 화면: 배지 "마지막 수신 N분 전", 연결됨이 아니면 "확인 불가" + 마지막 값 흐리게
  - Docker 확인(오프라인 기준 2분으로 줄여서): 끊김 10초 안에 일시 끊김 → 약 2분 뒤 오프라인 + 이상 → 복구 12초 안에 연결됨 + 이상 해결("오프라인 3분"), 끊긴 동안 쌓인 측정값은 늦은 측정값으로 들어옴
  - 서버 테스트 42개(상태 전이 단위 5개, 통합 3개 추가)
  - 리뷰 반영: 무수신 검사를 게이트웨이마다 따로 트랜잭션으로(하나가 실패해도 다른 게이트웨이는 롤백되지 않고, 잠금도 짧게). 일시 끊김 → 연결됨(30분 전 재연결) 단위 테스트 추가. 배지 문구 "설치 대기"는 용어집이 피하라는 말이라 "아직 받은 적 없음"으로. 설정 record에서 읽지 않는 값 제거. 시뮬레이터가 online 보고에 실패하면 연결을 끊고 다시 시도(예전 offline이 retained로 남지 않게). 스펙 4.4(버전은 gateway 테이블) 고침. 서버 테스트 43개
  - 미룬 것: 스펙 6.3의 복구 이력("오프라인 47분")은 지금 로그와 이상의 열림·해결 시각으로만 남는다. 화면에 이력 표시는 시연 마무리(#14)에서 판단

### #61 #5 지금 상태 규칙 (CO2, 목표 풍량, 바이패스)
- **내가 한 말**: 결정 7가지를 추천대로 시작하자고 했다.
- **결론**
  - "N분 지속" = 최신 측정값부터 조건을 만족하는 측정값이 끊기지 않고 이어진 구간. 2분 넘게 비면 끊김(늦은 측정값을 뺀 빈자리를 이어 붙이지 않기 위해)
  - 측정값은 규칙들이 밝힌 조회 범위 중 가장 긴 만큼 시간으로 가져오고, 늦은 측정값은 규칙 안에서 뺀다
  - CO2: 1,000 초과 10분 → 주의, 열린 동안 1,500 초과 → 같은 이상을 심각으로 올림(내리지 않음), 900 미만 10분 → 해제
  - 목표 풍량 미달: 80% 미만 30분 → 주의, 80% 이상 하나면 해제, 바이패스 중 제외. 부스트 중 제외는 #8
  - 바이패스 지속: 60분 → 주의, 꺼지면 해제
  - 최소 환기량 계산(인원 × 30과 면적 × 2.5 × 0.6 중 큰 값 올림)은 현장 엔티티에, 현장 API·화면에 표시, 시드 값 검증
  - 시뮬레이터 시나리오 6개(co2-high/normal, airflow-low/normal, bypass-on/off)
  - 테스트: 규칙 단위 테스트(경계, 히스테리시스, 늦은 값 제외, 빈 구간), 계산 테스트, CO2 통합 테스트 1개(측정 시각을 지금 이후로 나눠 보내 기다리지 않음). 서버 66개, 시뮬레이터 12개
  - TDD로 잡은 것: 다른 테스트가 남긴 "1분 뒤 측정값"이 같은 장비의 뒤 테스트에 섞여 실패 → 테스트 전용 장비, 끝나면 미래 시각 측정값 지우기
  - Docker(지속 2분): 세 이상 모두 열림, CO2는 주의 → 심각으로 올라감. 풍량·바이패스는 정상화 즉시 해제
  - Docker에서 찾은 시뮬레이터 버그: CO2를 정상으로 돌려도 950 근처에 머물러 해제 기준(900 미만)을 오르내림 → 750까지 내려오게 고침, 테스트 추가 → 해제 확인
  - 환경 문제: 바탕화면이 iCloud 동기화라 #4·#6에서 지우거나 옮긴 옛 파일 5개가 되살아나 Docker 앱이 뜨지 않음(엔티티 이름 중복). 지우고 다시 확인. 빌드 전 `git status`로 모르는 파일 확인하기로 함
  - 리뷰 반영: 조회 범위가 비었을 때 가져오던 "최신 1개"가 몇 시간 전 값이라 풍량·바이패스 이상을 잘못 해제할 수 있었다 → 범위 밖 값은 쓰지 않음. 바이패스는 스펙대로 "60분 넘게"(딱 60분은 아님). 설명 문구를 "N분 이상 이어짐"으로 맞추고 1분 미만 설정이면 "N초". 심각도 올릴 때 설명도 바꾸는 것을 ADR-0013에 예외로 기록. 최소 환기량 계산은 현장 엔티티로 옮김(서비스 레이어는 유스케이스만). 지속 판단 도우미 이름을 `AnomalyRuleStreak`로. 심각도를 내리지 않는지 단위 테스트 추가. 시뮬레이터 평소 CO2 상한을 880으로(해제 기준 900보다 낮게). 서버 테스트 67개
  - 미룬 것: 주의로 열린 뒤 CO2가 잠깐 1,000 아래로 내려갔다 다시 오르면, 다시 이어진 시간이 기준을 채운 뒤에 심각이 된다(스펙에 기록). 테스트 전용 장비가 테스트 DB에 남는 것은 그대로 둠

### #62 #7 후드 연동 감시
- **내가 한 말**: 결정 7가지를 추천대로 시작하자고 했다.
- **결론**
  - 새 기능 패키지 `vent/hood/`. VEMC가 보낸 HOOD_ON/OFF를 `device_event`(V8)에 저장(messageId 중복 무시), 확인 결과를 같은 행에 기록
  - 확인: HOOD_ON 직전 급기와 60초 뒤 첫 급기 비교, 10% 넘게 오르면 정상, 아니면 무반응. 늦은 측정값도 씀(끊긴 동안의 연동도 나중에 확인)
  - 확인 보류: 60초 안에 꺼짐, 이후 값이 꺼진 뒤에 잰 값, 직전 값 없음, 24시간 동안 이후 값 없음
  - VEMC 무반응 이상은 VEMC에 붙고, 다음 연동이 정상이면 해제. 확인 기록과 같은 트랜잭션(ADR-0014와 같은 방식)
  - 시뮬레이터: hood-on/off(연동은 시뮬레이터 안에서, 급기 +40%·배기 −20%), vemc-fail/repair(이벤트는 가지만 급기 그대로), 이벤트도 끊긴 동안 버퍼에
  - 덤으로 고친 것: #5 이상 설명 "10분 이상 이어짐" → "10분 동안 이어짐"(용어집: "이상"은 Anomaly 뜻으로만)
  - 테스트: 확인 단위 7개, 통합 3개(30~40분 전 늦은 측정값으로 확인, 중복 이벤트 한 번 저장, 환기장치가 보낸 이벤트 거절). 서버 77개, 시뮬레이터 13개
  - Docker: 정상 연동 → 정상, VEMC 고장 → 무반응 + 이상, 수리 후 다음 연동 정상 → 해제, 끊긴 동안 후드 ON → 다시 연결된 뒤 정상
  - 리뷰 반영: 확인 순서 버그(HOOD_ON이 직전 측정값보다 먼저 저장된 30초 사이에 검사가 돌면 영구히 보류로 닫힘) → 60초 뒤 값을 먼저 기다림. HOOD_ON 연속(사이에 HOOD_OFF 없음)은 직전 급기가 이미 올라 있어 무반응으로 잘못 나옴 → 확인 보류, 시뮬레이터도 켜진 후드에 다시 보내지 않음. 직전·이후 값이 2분 넘게 떨어져 있으면 보류(측정값이 빠진 구간). 이상이 열린 뒤의 정상만 해결로. 이상 설명의 "60초"를 설정값으로. 확인 재료를 record 하나로(`HoodInterlockInput`). 테스트는 전용 현장(90번)을 등록해 다른 테스트와 섞이지 않게. 서버 79개, 시뮬레이터 13개
  - 용어 충돌: 용어집에서 "판정"은 직원의 A/S 판정(Verdict)이라, 후드 쪽은 "연동 확인", "확인 보류"로 바꿈
  - Docker에서 덤으로 확인한 것: V8 주석을 고쳐 체크섬이 달라져 앱이 안 뜸(커밋 전이라 고쳐도 되는 파일, 로컬 DB에서 V8만 지우고 다시 적용). 앱이 꺼진 동안 브로커가 보관한 이벤트가 앱을 켜자 순서대로 처리되어 무반응 → 이상 → 다음 연동 정상 → 해결까지 이어짐
  - 미룬 것: 한 현장에 환기장치가 여러 대일 때 어느 장비와 비교할지(지금은 ID가 가장 앞선 장비), 이벤트 시각의 시계 오차 검사, 수신 검사(장비 ID·현장 일치) 공통화

### #63 #13 브로커 계정과 ACL
- **내가 한 말**: 결정 6가지를 그대로 진행하자고 했다.
- **결론**
  - 익명 접속 거부, 계정별 ACL을 직접 적음(최소 권한: 게이트웨이는 자기 현장 보고 토픽만 쓰고 자기 현장 명령만 받음, 명령은 서버만 보냄)
  - 비밀번호(해시도)를 저장소에 두지 않음: 브로커 시작 스크립트가 환경변수로 비밀번호 파일을 만듦. 기본값은 시연용
  - `use_username_as_clientid`: 계정만 있으면 다른 클라이언트 ID로 접속해 남의 연결을 끊는 것을 막음
  - 서버 `vent.mqtt.username/password`(비어 있으면 익명, 통합 테스트용), 시뮬레이터 게이트웨이별 계정
  - 테스트: 저장소의 실제 브로커 설정으로 Mosquitto를 띄워 익명·틀린 비밀번호 거부, 자기 현장만 발행, 다른 현장 명령 못 받음, 게이트웨이의 명령 위조 차단 확인(4개). 기능 통합 테스트는 익명 브로커 그대로. 서버 83개
  - Docker: 익명 발행 exit 5, gw-s1 계정으로 현장 2 토픽 발행 → PUBACK RC:135(Not authorized), 서버에 저장 0건
  - 덤으로 본 것: 공격 흉내로 gw-s1 계정을 쓰자 브로커가 클라이언트 ID를 gw-s1로 바꿔 진짜 gw-s1이 "session taken over"로 잠깐 끊김 → 계정 이름 고정의 대가. 계정은 게이트웨이마다 따로, 운영은 장비별 인증서
  - TLS·장비별 인증서·비밀 관리·대규모 ACL은 README에 운영 대응으로
  - 리뷰 반영: 계정만 넣고 비밀번호가 비거나 client-id와 계정 이름이 다르면 서버가 시작할 때 멈춤(조용히 재시도만 반복하지 않게), 설정을 로그에 찍어도 비밀번호는 가림. 브로커·DB 포트는 127.0.0.1에서만(시연 비밀번호가 공개돼 있어서). 상태 토픽은 자기 게이트웨이 ID로만 쓰게. "받지 못한다" 테스트마다 같은 연결로 허용된 메시지(canary)를 보내 연결이 살아 있는 것을 함께 확인, 거부 이유 코드(134/135)까지 확인. 비밀번호·ACL 파일을 0600으로(Mosquitto 2 경고 제거). README 개발 실행에 서버 계정 추가
  - 미룬 것: 서버 리스너의 구독 토픽과 ACL을 자동으로 맞춰 보는 테스트(지금은 ACL 테스트가 토픽을 직접 적음), 현장 추가 시 고칠 곳이 여러 군데(ACL, 시작 스크립트, compose, 시뮬레이터)인 것은 dynamic security로 옮길 때 해결

### #64 #8 부스트 기본 왕복 (토요일 저녁, 일요일 할당량을 먼저 시작)
- **내가 한 말**: 결정 7가지를 진행하자고 했다.
- **결론**

### #65 #9 원격 명령 신뢰성
- **내가 한 말**: 결정 7가지를 진행하자고 했다.
- **결론**
  - V10: 시간 초과·밀려남 상태, 만료 시각, 재시도 횟수·시각, 늦은 응답. #8에서 이름 붙여 둔 제약을 지우고 다시 만듦

  - 밀려남: 새 요청이 오면 기다리던 명령을 같은 트랜잭션에서 SUPERSEDED. 밀린 명령 응답은 무시
  - 늦은 응답: 시간 초과 뒤 적용·거절이 오면 실제 결과 + late_ack, COMMAND_TIMEOUT 해제
  - 만료: MQTT 5 메시지 만료를 남은 시간으로(재시도가 만료를 늘리지 않게), 장비도 expiresAt 검사
  - 장비: 세션 유지(이게 없으면 끊긴 동안 온 명령을 브로커가 버려 "몰림" 자체가 안 생김), 0.5초 묶음, 최신 하나만 적용, commandId 100개 기억, 응답 버퍼
  - 시나리오 `network-silent`: Last Will 없이 끊어 서버가 모르는 상태를 만듦
  - 테스트: 재시도 판단 3개, 상태 바꾸기 5개, 통합 2개(재시도·시간 초과·늦은 응답·만료, 밀려남), 장비 명령 처리 5개. 서버 105개, 시뮬레이터 21개

  - 리뷰 반영: 같은 장비에 부스트 요청 두 개가 동시에 오면 대기 명령이 둘 남을 수 있었다(잠글 기존 행이 없으면 잠금이 안 걸림) → 장비 행을 잠가 요청을 한 줄로 세우고, DB 부분 유니크 인덱스(장비당 SENT 하나)로 한 번 더. 이때 Hibernate가 INSERT를 UPDATE보다 먼저 보내 인덱스에 걸리는 것을 막으려고 밀어낸 뒤 flush. 이미 만료된 명령은 재시도하지 않고 바로 시간 초과(서버가 멈췄다 깨어난 경우). V10에서 #8 때 남은 만료 명령을 시간 초과로 닫아 가짜 이상 방지. 재시도 판단 입력을 record로. 시뮬레이터: 요청 시각 없는 명령은 INVALID, 묶음 처리 예외로 묶음 전체가 조용히 사라지지 않게. 테스트: 늦은 거절, "다음 명령 정상"으로 해제. 서버 107개, 시뮬레이터 22개
  - 미룬 것: 시간 초과 처리(스케줄러)와 같은 장비의 다른 명령 응답이 동시에 돌면 응답 쪽이 아직 커밋 안 된 이상을 못 봐 해제를 놓칠 수 있음(창이 좁고 다음 응답에서 풀림). 재시도 시 메시지 만료가 남은 시간으로 줄어드는지 자동 테스트는 없음(Docker 로그로 확인: 만료까지 49초)
  - Docker: V10을 고쳐 로컬 DB를 새로 만듦(docker compose down -v, 시드 다시 들어감). 몰림 시나리오 다시 확인

### #67 #11 판정
- **내가 한 말**: 결정 7가지를 추천대로 진행하자고 했다. 내가 결정 질문을 영어로 써서 한국어로 다시 정리해 달라고 했다.
- **결론**
  - `servicerequest` 안에 판정(V12 `verdict`): AI 소견과 같은 항목(원인, 조치, 부품, 방문, 권하는 점검, 고객 안내) + 고쳤는지 + 고친 항목 + 담당자

  - 용어: "승인"은 판정의 피할 말이라 버튼을 "그대로 판정 / 고쳐서 판정 / 판정"으로
  - 고객용 안내 조회: 판정 전에는 비어 있고 판정 뒤에만 확정 안내(ADR-0005를 API로)
  - 화면: 상세에 판정 양식(AI 소견으로 미리 채움, 부품 체크박스, 담당자 이름 기억), 판정 내용, "고객 화면" 미리보기

  - 미룬 것: 판정 뒤 고객에게 실제로 보내는 알림(문자·카카오)은 MVP 범위 밖. 판정 수정·취소 없음

### #68 #12 실제 Claude 연결과 평가 세트

### #70 #15 복기: MQTT, 웹소켓, Kafka, HTTP
- **내가 한 말**: 복습 2번에 들어가기 전에, MQTT가 무엇인지 구조도를 그려서 왜 쓰는지, 양방향이면 왜 웹소켓을 안 쓰는지, 데이터가 중요하면 쓸 수 있는 Kafka는 무엇인지, IoT에 왜 MQTT를 쓰고 HTTP와 무엇이 다른지 설명해 달라고 했다.
- **결론**

### #71 #15 복습 2번: QoS 1 중복
- **내가 한 말**: QoS 0은 최대 한 번, 1은 최소 한 번, 2는 정확히 한 번. 무수신이나 네트워크 끊김이면 멱등성으로 또 보낼 수 있어서 1을 골랐다고 답했다.
- **결론**
  - 맞은 것: QoS 세 단계 정의, 확인을 못 받으면 다시 보낸다는 방향
  - 고친 것: 멱등성은 "다시 보내는 것"이 아니라 받는 쪽이 같은 메시지를 여러 번 받아도 결과가 한 번과 같게 만드는 성질. 보내는 쪽은 재전송, 받는 쪽은 멱등 처리
  - 채운 것: 중복은 메시지는 도착했는데 PUBACK만 잃어버릴 때 생긴다(보내는 쪽은 둘을 구분 못 함). 막는 방법은 게이트웨이가 만든 messageId(UUID) + `message_id` 유니크 + `ON CONFLICT DO NOTHING` → 0행이면 DUPLICATE, 확인 응답은 보냄. QoS 2를 안 쓴 이유: 4단계 왕복, 구간별 보장일 뿐 DB까지는 아님, 오프라인 버퍼 재전송은 MQTT에겐 새 메시지라 QoS 2로도 못 막음

### #77 #15 "DB가 죽는다"는 어떤 상황인가
- **내가 한 말**: 면접 질문에 "DB가 죽는다"는 표현이 있는데, RDS나 외부 서버에 DB를 올렸을 때를 가정한 것인지 물었다.
- **결론**
  - RDS만이 아니다. 서버가 DB에 잠깐 연결하지 못하는 모든 경우다. 같은 컴퓨터의 postgres 컨테이너도 서버 입장에서는 TCP 5432 너머의 다른 프로세스라 똑같이 끊길 수 있다
  - 예: DB 재시작·배포, RDS 장애 조치, 네트워크·보안 그룹 문제, 디스크 가득·메모리 부족, 커넥션 풀 고갈(DB는 살아 있는데 연결을 못 얻음)
  - 우리 처리: 연결 실패 같은 잠깐의 오류는 PUBACK을 보내지 않고 재연결해서 다시 받는다(ADR-0012). 형식 오류·무결성 위반은 다시 해도 같으니 버린다
  - interview-questions.md 해당 질문에 설명 두 줄 추가

### #78 #15 평소에 DB가 죽을 일이 있나
- **내가 한 말**: 일반적인 상황에서 DB가 죽을 일이 있는지 물었다.
- **결론**
  - DB가 완전히 꺼지는 일은 드물다. 하지만 "잠깐 연결을 못 하는 일"은 계획된 작업(버전 업데이트, 사양 변경, RDS 유지보수)과 흔한 사고(커넥션 풀 고갈, 긴 트랜잭션의 잠금 대기, 디스크 가득, 연결 수 한도 초과)로 자주 생긴다 [일반]
  - IoT는 데이터가 쉬지 않고 들어와서, 몇 초만 끊겨도 그 사이 메시지가 쌓인다. 확률이 낮아도 장비가 많으면 반드시 마주친다
