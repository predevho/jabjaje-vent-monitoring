- 각 질문 아래 **답변 포인트**는 외우는 문장이 아니라 말할 순서다. 내 말로 바꿔서 연습한다.

## 1. 회사와 도메인

**Q. 우리 회사가 뭘 하는 회사인지 알고 있나요?**
- 패시브하우스용 열회수 환기장치(KOMFOVENT), 복사냉방, 기밀·단열 자재 유통
- TAB, 블로어도어 테스트, WUFI 같은 검증 서비스, 환기량 산정 계산기
- 자체 컨트롤러 VEMC가 있고, 이걸 IoT 플랫폼으로 확장하려는 단계로 이해했다 (#1)

**Q. 이 사이드프로젝트를 왜 만들었나요?**
- 주요 업무 4개(IoT 플랫폼, 모바일, 사내 자동화, 안정성)를 하나의 데모로 보여주고 싶었다
- 설치된 환기장치는 고객이 문의하기 전까지 상태를 알 수 없다는 문제에서 출발했다
- 문제 정의 → 핵심 기능 MVP → 리스크 검토 순서로 진행했다 (공고의 "왜 필요한가", "점진적 실행력")

**Q. VEMC가 하는 일을 설명해 보세요.**
- 후드나 화장실 배기팬이 켜지면 환기장치에 신호를 보내 급기를 올리고 배기를 내린다
- 실내 압력 균형을 지켜 오염 공기가 다른 공간으로 퍼지는 것을 막는다 (#8)

**Q. 필요 환기량은 어떻게 계산했나요?**
- 회사 산정 기준: 인원 × 30CMH와 면적 × 층고 2.5m × 0.6회/h 중 큰 값
- 설치 후 TAB 측정값이 있으면 그 값을 우선한다 (#11)

## 2. 아키텍처

**Q. 전체 구조를 설명해 보세요.**
- 집 안: 후드-VEMC-환기장치는 전선으로 현장 연동, 게이트웨이가 MQTT로 클라우드에 보고
- 서버: Spring Boot 하나, 기능별 패키지(ingest, device, alert, command, diagnosis, web)
- 저장: PostgreSQL (#7, #11)

**Q. 왜 마이크로서비스가 아니라 하나의 앱인가요?**
- 1인 개발, 4일, 11명 회사 규모에서는 오버스펙
- 패키지 경계를 나눠두어 장비가 늘면 수집(ingest)만 분리할 수 있다 (#3~#4)

**Q. 후드 연동을 왜 서버에서 처리하지 않았나요?**
- 인터넷이 끊기면 연동이 멈추고, 그게 VEMC가 막으려던 문제다
- 안전과 관련된 제어는 현장, 클라우드는 감시와 편의 기능 (#8, #9)

## 3. MQTT와 통신

**Q. 게이트웨이가 정확히 뭐고, 몇 계층 장비인가요?**
- 현장마다 하나 있는 물리 기기. 환기장치와는 Modbus(RS-485), 서버와는 MQTT(TCP/IP)로 통신
- 7계층에서 프로토콜을 바꿔주는 응용 계층 게이트웨이. 공유기(3계층), 스위치(2계층)와 다르다
- 데이터에서는 장비와 분리했다. 게이트웨이가 끊겨도 환기장치는 "확인 불가"일 뿐 오프라인이 아니다 (#28)

**Q. 왜 HTTP 대신 MQTT를 썼나요?**
- 장비가 먼저 브로커에 연결하므로 공유기(NAT) 뒤 장비에도 명령을 보낼 수 있다
- 가벼운 헤더, QoS로 전달 보장 수준 선택, Last Will로 끊김 감지 (#5)

**Q. MQTT와 웹소켓은 무엇이 다른가요?**
- 둘 다 연결 하나로 양방향이다. 웹소켓은 두 쪽이 직접 연결되고, MQTT는 모두가 브로커와만 연결해 토픽으로 주고받는다
- MQTT는 여러 구독자에게 한 번에 전달, 상대가 꺼져 있어도 브로커 보관, QoS·keepalive·Last Will 기본 제공 → IoT에 맞다
- 우리 화면은 HTTP 폴링. 측정 주기가 30초라 충분하고, 브라우저에 브로커 권한을 주지 않아도 된다 (#51)

**Q. QoS 0, 1, 2의 차이와 무엇을 골랐는지?**
- 0: 한 번 보내고 끝, 1: 최소 한 번(중복 가능), 2: 정확히 한 번(느림)
- QoS 1을 쓰고 중복은 messageId 유니크 제약으로 걸러낸다 (#7)

**Q. 인터넷이 끊기면 어떻게 되나요?**
- 현장 연동은 계속 동작, 게이트웨이가 데이터를 로컬 버퍼에 쌓았다가 복구 후 업로드
- 측정 시각 기준으로 저장해서 그래프 구멍이 생기지 않는다 (#9)

**Q. 오프라인을 어떻게 감지하고 보여주나요?**
- Last Will + 2분 무수신 검사(half-open TCP 대비)
- 2분부터 화면 표시, 30분부터 직원 알림. Wi-Fi의 짧은 끊김마다 알림이 쌓이지 않게 (#12)

**Q. 오프라인 동안 쌓인 명령이 한꺼번에 오면?**
- 서버: 장비당 대기 명령 1개, 명령은 "원하는 상태"로
- 브로커: MQTT 5 메시지 만료
- 장비: 만료 무시, 중복 무시, 최신 하나만 적용
- 확장: 디바이스 섀도(desired/reported) (#12)

**Q. 명령 응답이 시간 초과된 뒤에 도착하면?**
- 실제 결과대로 APPLIED로 바꾸고 late_ack 표시, 타임아웃 알림 해제 (#12)

## 4. 데이터

**Q. 환기장치에서 어떤 데이터를 수집하나요?**
- 30초마다 7가지: CO2, 온도, 습도, 급기·배기 풍량, 필터 차압, 바이패스 여부
- 각각이 어떤 이상 규칙으로 이어지는지 설명: 예) 필터 차압 상승 + 급기 하락 → 필터 막힘을 고객 문의 전에 감지
- 후드 ON/OFF는 측정값이 아니라 이벤트로 따로 받는다 (#43)


**Q. 측정 시각과 수신 시각을 왜 따로 저장하나요?**
- 통신 지연, 버퍼 재전송을 구분할 수 있고, 늦게 온 데이터도 제자리에 저장된다 (#7)

**Q. 늦게 온 데이터로 알림이 뜨면 문제 아닌가요?**
- 지금 상태를 나타내는 규칙(CO2, 풍량)은 최근 데이터로만 판단
- 고장 판정(VEMC 무반응)은 늦은 데이터도 쓴다 (#11)

**Q. 데이터가 많아지면 어떻게 하나요?**
- 지금은 하루 약 8,600건이라 일반 테이블 + 인덱스로 충분
- 수백만 건/일이 되면 파티셔닝이나 TimescaleDB, 원본 90일 후 1시간 집계 (#7, #11)

**Q. 센서 값이 이상하면?**
- 범위 검증 후 OUT_OF_RANGE로 표시하고 알림 판단에서 제외, 시계 오차는 CLOCK_SKEW (#11)

## 5. 신뢰성과 장애

**Q. 알림이 켜졌다 꺼졌다 반복하면?**
- 히스테리시스: 발생 1,000ppm, 해제 900ppm
- 열린 알림은 장비·규칙당 하나 (부분 유니크 인덱스) (#8)

**Q. 이상 판단 코드가 실패하면 측정값 저장도 실패하나요?**
- 아니다. 측정값 저장이 커밋된 뒤 이벤트(`@TransactionalEventListener(AFTER_COMMIT)`)로 받아서 새 트랜잭션에서 평가한다 (ADR-0013)
- 같은 트랜잭션이면 규칙 버그 하나로 측정값까지 롤백된다. 측정값이 이상보다 중요하다
- 평가가 실패하면 로그만 남긴다. 평가는 DB의 최신 값을 다시 읽으므로 다음 측정값(30초 뒤)에서 따라잡는다 (#57)

**Q. 늦게 들어온 옛날 측정값 때문에 이상이 잘못 해제되지 않나요?**
- 방금 받은 값이 아니라 측정 시각 기준 가장 최신인 OK 값으로 판단한다
- 필터 막힘이 열린 뒤 교체 전 시각의 정상 값이 늦게 들어와도 해제되지 않는 것을 테스트로 확인했다 (#57)

**Q. 서버를 여러 대 띄우면 같은 이상이 두 번 열리지 않나요?**
- 서비스는 "열린 이상이 있나 조회 → 없으면 저장"이라 두 서버가 동시에 조회하면 둘 다 저장하려 할 수 있다
- DB의 부분 유니크 인덱스(열린 이상만, 장비·규칙마다 하나)가 두 번째 저장을 거부한다. 그 평가는 롤백되고 다음 측정값에서 다시 판단하면 이미 열린 것을 찾는다
- 더 깔끔하게 하려면 `INSERT ... ON CONFLICT DO NOTHING`으로 조회와 저장을 한 번에 한다. 측정값 중복 저장에 이미 쓰고 있는 방식이다 (#57)

**Q. 연결 상태 관리에 Redis를 쓰지 않은 이유는?**
- 상태와 이상이 둘 다 PostgreSQL에 있어 트랜잭션 하나로 함께 바뀐다. Redis를 넣으면 두 저장소에 나눠 쓰게 되고, Lua 스크립트는 Redis 안에서만 원자적이라 한쪽만 성공하는 문제가 생긴다
- 동시 수정은 행 잠금(`SELECT ... FOR UPDATE`)으로 막았고, 서버가 여러 대여도 DB 잠금이라 그대로 통한다
- 장비가 수만 대로 늘면 마지막 수신 시각만 Redis Sorted Set에 두고, 무수신 검사는 `ZRANGEBYSCORE`로 오래된 것만 찾는다. DB에는 상태가 바뀔 때만 쓴다. 쓰기 부하를 줄이는 게 목적이다 (#59)

**Q. 저장 중에 DB가 죽으면 측정값은 어떻게 되나요?**
- #2 코드 리뷰에서 실제로 찾은 빈틈: 저장이 실패해도 브로커에 수신 확인(PUBACK)을 보내서 측정값이 사라졌다
- 수동 확인 응답(manual ack)으로 저장 성공 후에만 응답하도록 바꿨다(#3). 실패한 메시지는 재연결 때 브로커가 다시 보낸다
- 같은 메시지가 다시 와도 messageId 중복 무시로 한 번만 저장된다 → "최소 한 번 전달 + 멱등 저장"

**Q. 실패한 메시지를 계속 다시 받으면 문제가 없나요?**
- 리뷰에서 실제로 찾은 버그: 모든 DB 오류를 재시도하다 보니, 센서 고장값이 컬럼 크기를 넘는 무결성 위반 메시지를 5초마다 끝없이 다시 받았다(poison message). 재연결 때마다 다른 현장 수신도 끊겼다
- 잠깐의 실패(연결 실패, 일시 오류)만 재시도하고, 영구 실패(형식, 무결성)는 로그를 남기고 버리도록 고쳤다. 컬럼도 넓혀 고장값을 범위 밖으로 저장한다
- "일어나지 않음"은 Awaitility `during()`으로 재연결 대기보다 길게 지켜보는 테스트로 확인했다 (#56)

**Q. 장비가 끊겼다 다시 붙으면 데이터는 어떻게 되나요?**
- 게이트웨이가 원형 버퍼(24시간분)에 쌓았다가 오래된 것부터 PUBACK을 받으며 하나씩 보낸다
- 재접속은 지수 백오프 + jitter라 브로커 재시작 때 한꺼번에 몰리지 않는다
- 서버는 측정 시각 그대로 저장하고 늦은 측정값으로 표시, 그래프에서 주황색으로 구분. 실제로 브로커를 150초 멈췄다 켜서 확인했다 (#55)

**Q. 테스트가 가끔 실패하는 문제는 없었나요?**
- 서버가 구독을 마치기 전에 테스트가 메시지를 보내 유실된 적이 있다. 서버가 준비 상태(연결 + 구독 완료)를 알려 주고, 테스트는 그걸 기다린 뒤 보내게 해서 고쳤다. 두 번 연속 돌려 같은 결과를 확인했다
- 측정 시각이 정확히 0초일 때만 실패하는(60번에 1번) 테스트를 찾았다. `toString()`이 0초를 생략해서였고 ISO 형식으로 비교하게 고쳤다
- 테스트가 로컬 시연 브로커에 같은 클라이언트 ID로 붙어 시연 서버를 끊을 수 있었다. MQTT가 필요 없는 테스트는 연결을 끄고, 필요한 테스트는 ID를 매번 다르게 했다 (#55)

**Q. 장비가 끊긴 것을 어떻게 알아요?**
- 두 경로: 게이트웨이가 연결할 때 등록한 Last Will(갑자기 끊기면 브로커가 offline을 대신 보냄)과, 서버의 30초 주기 무수신 검사(2분 넘게 못 받으면)
- Last Will만으로는 부족하다. Wi-Fi가 꺼져도 TCP가 끊긴 줄 모르는 경우(half-open)에는 keepalive가 끝날 때까지 안 나간다
- 2분이면 "일시 끊김"으로 화면에만, 30분이 넘으면 "오프라인" 이상. 가정용 Wi-Fi의 짧은 끊김마다 이상이 쌓이지 않게 했다 (#60)

**Q. 서버가 재시작하면 옛날 online 메시지 때문에 끊긴 장비가 연결됨으로 보이지 않나요?**
- 상태 토픽은 retained라 다시 구독하면 브로커가 마지막 메시지를 준다. retain 플래그로 구분해서, retained online은 버전·지원 기능만 기록하고 연결 상태는 바꾸지 않는다
- offline은 retained여도 반영한다. 서버가 꺼진 동안 Last Will이 나갔다는 뜻이다 (#60)

**Q. 스케줄러와 메시지 수신이 같은 데이터를 동시에 바꾸면?**
- 검사가 "2분 지남"을 읽은 직후 측정값이 "연결됨"으로 커밋되면, 검사가 그 위에 "일시 끊김"을 덮어쓸 수 있다(lost update)
- 두 경로 모두 행 잠금(`SELECT ... FOR UPDATE`)으로 읽고, 잠근 뒤 조건을 다시 확인한다. DB 잠금이라 서버가 여러 대여도 통한다
- 낙관적 잠금(`@Version`)도 가능하지만 충돌 시 재시도가 필요하고, 현장 수가 적어 비관적 잠금이 더 단순했다 (#60)

**Q. 오프라인 이상은 왜 측정값 이상과 다르게 같은 트랜잭션에서 만들었나요?**
- 측정값은 이상보다 중요해서 분리했다(평가가 실패해도 측정값은 남게)
- 연결 상태는 이상과 항상 같이 움직여야 한다. 상태만 오프라인으로 커밋되고 이상이 빠지면 다음 검사는 "이미 오프라인"이라 다시 만들지 않는다
- 받는 서비스에 `Propagation.MANDATORY`를 붙여 트랜잭션 밖에서 부르면 바로 예외가 나게 했다 (ADR-0014, #60)

**Q. "CO2가 10분 넘게 1,000ppm 초과"는 어떻게 판단했나요?**
- 최신 측정값부터 거꾸로 가며 조건을 만족하는 값이 끊기지 않고 이어진 구간을 찾고, 그 길이(측정 시각 기준)가 10분 이상인지 본다
- 측정값 사이가 2분 넘게 비면 끊긴 것으로 본다. 끊긴 동안 쌓였다 늦게 온 값은 지금 상태 판단에서 빼기 때문에, 빈자리를 이어 붙이면 옛날 값으로 지금 이상이 생긴다
- 상태를 메모리에 두지 않고 매번 DB에서 최근 측정값을 읽어 판단한다. 서버가 재시작돼도 판단이 이어진다 (#61)

**Q. 10분, 30분, 60분 규칙은 어떻게 테스트했나요?**
- 규칙은 DB를 모르는 순수 클래스라, 측정 시각을 직접 넣어 경계(9분 30초는 안 되고 10분은 됨, 1,000 정각은 초과 아님)를 단위 테스트했다
- 통합 테스트는 지속 시간 설정을 1분으로 줄이고 측정 시각을 30초 간격으로 "지금 이후"로 나눠 보냈다. 실제로 기다리지 않는다
- 이때 다른 테스트가 남긴 미래 시각 데이터가 섞여 실패했고, 테스트 전용 장비와 정리 코드로 격리했다 (#61)

**Q. 후드 연동이 제대로 됐는지 서버는 어떻게 아나요?**
- 연동 자체는 현장에서(VEMC → 환기장치) 일어나고, VEMC는 "후드 켜짐" 이벤트만 서버에 보낸다
- 서버는 30초마다 확인 전 이벤트를 찾아, 같은 현장 환기장치의 직전 급기와 60초 뒤 첫 급기를 비교한다. 10% 넘게 오르면 정상, 아니면 VEMC 무반응 이상
- 비교할 값이 없거나 후드를 60초 안에 끄면 "확인 보류"로 둔다. 무반응으로 몰면 오탐이다 (#62)

**Q. 인터넷이 끊긴 동안 후드를 켜면요?**
- 연동은 현장에서 그대로 일어난다. 게이트웨이가 이벤트와 측정값을 버퍼에 쌓았다가 다시 연결되면 원래 시각 그대로 보낸다
- 확인은 장비 시각으로 하고 늦은 측정값도 쓰므로, 복구 뒤에 "끊긴 동안 연동이 정상이었다"를 확인할 수 있다. 24시간(버퍼 크기)이 지나도 값이 없으면 확인 보류 (#62)

**Q. 서버가 재시작되면 메시지가 유실되지 않나요?**
- persistent session + QoS 1이면 브로커가 보관
- 알림 판단 상태를 메모리에 두지 않고 DB를 조회 (#11)

**Q. 브로커가 죽으면?**
- MVP는 단일 브로커. 운영에서는 매니지드 IoT 서비스나 클러스터
- 게이트웨이는 지수 백오프 + jitter로 재접속 (#11)

**Q. 원격 명령은 어떤 순서로 저장하고 보내나요?**
- 보내기 전 검사(지원 기능, 최대 풍량, 2시간, 연결 상태) → 명령을 "보냄"으로 저장 → 커밋된 뒤 발행(QoS 1, retained 없음) → 장비가 적용·거절 응답 → 상태 반영
- 먼저 발행하고 저장이 실패하면 장비는 서버가 모르는 명령을 적용한다. 그래서 커밋 뒤에 보낸다. 발행이 실패하면 "보냄"으로 남고 재시도와 시간 초과가 처리한다
- 저장과 발행을 완전히 묶으려면 아웃박스 패턴을 쓴다 (#64)

**Q. 부스트를 보냈는데 장비가 거절하면요?**
- 장비가 우선순위로 판단한다: 자기 보호(동결 방지) > 현장 후드 연동 > 원격 명령. 거절 사유(FROST_PROTECTION, HOOD_INTERLOCK)를 응답에 담고, 화면에 "거절됨 · 동결 방지 중"으로 보인다
- 게이트웨이가 끊겨 있으면 서버가 아예 보내지 않고 "지금은 연결이 끊겨 명령을 보낼 수 없어요"로 안내한다 (#64)

**Q. 장비가 원격 명령에 응답하지 않으면요?**
- 10초 기다렸다가 같은 commandId로 한 번 다시 보낸다. 그래도 10초 응답이 없으면 시간 초과로 바꾸고 "원격 명령 시간 초과" 이상(정보)을 연다
- 장비가 나중에라도 응답하면 실제 결과로 바꾸고 "늦게 적용됨"으로 보여 주며 이상을 해제한다
- 같은 명령이 두 번 가도 장비가 commandId를 기억해 한 번만 적용한다(최소 한 번 전달 + 멱등) (#65)

**Q. 인터넷이 끊긴 동안 부스트를 여러 번 누르면, 다시 연결될 때 전부 실행되나요?**
- 아니다. 명령을 "원하는 상태"로 본다. 서버는 장비당 대기 명령을 하나만 두고(이전 것은 밀려남), 모든 명령은 60초 뒤 만료된다(MQTT 5 메시지 만료 + 장비 검사)
- 장비는 몰려온 명령을 0.5초 모아 가장 최신 하나만 적용하고 나머지는 거절한다
- 실제로 Last Will 없이 끊는 시나리오로 부스트 3번 → 재연결했을 때 최신 하나만 적용되는 것을 확인했다
- 장비가 많아지면 AWS IoT Device Shadow 같은 desired/reported 방식으로 확장한다 (#65)

## 6. 보안

**Q. 누군가 남의 집 환기장치에 명령을 보내면?**
- 게이트웨이별 계정과 ACL로 자기 토픽만 허용, 장비 ID는 토픽에서 읽는다
- 운영에서는 TLS와 장비별 인증서 (#11)

**Q. 환기 데이터에 개인정보 문제는 없나요?**
- CO2 패턴으로 집이 비는 시간을 추정할 수 있다 → 접근 권한, 보관 기간, AI에 개인정보 미전송 (#11)

**Q. 다른 집 환기장치에 명령을 보내지 못하게 어떻게 막았나요?**
- 브로커에서 막는다. 익명 접속을 거부하고 게이트웨이마다 계정을 두었다. ACL로 자기 현장 토픽에만 보고하고 자기 현장 명령만 받게 했다. 명령은 서버 계정만 보낼 수 있다(최소 권한)
- 서버도 한 번 더 막는다. 장비 ID는 토픽에서 읽고, 메시지의 장비 ID나 현장이 토픽과 다르면 버린다
- 현장 1 계정으로 현장 2 토픽에 보내면 브로커가 PUBACK 135(Not authorized)로 거부하는 것을 실제 브로커 설정으로 테스트했다 (#63)

**Q. 비밀번호는 어디에 두나요? 운영에서는요?**
- 해시도 저장소에 두지 않고, 브로커가 시작할 때 환경변수로 비밀번호 파일을 만든다
- 운영에서는 TLS(8883)를 켜고 게이트웨이마다 인증서를 발급해 비밀번호 대신 쓴다(mTLS). 키는 비밀 관리 서비스에서 주입하고, 잃어버린 장비는 인증서를 폐기한다
- 현장이 많아지면 ACL 파일 대신 dynamic security 플러그인이나 AWS IoT Core 같은 매니지드 서비스 정책으로 옮긴다 (#63)

## 7. AI 활용과 검증 (공고 핵심)

**Q. AI를 어디에 썼고, 결과를 어떻게 믿나요?**
- A/S 1차 진단: 숫자 계산은 코드, AI는 해석만
- 근거 지표가 실제 데이터에 있는지, 부품이 판매 목록에 있는지 코드로 검증
- 직원 승인 후에만 고객에게 안내, 평가 세트 5개 시나리오로 정확도 확인 (#10)

**Q. 고객이 문의에 이상한 지시를 넣으면?**
- 구분 태그로 데이터 취급, 출력에서 금액·무상 교체 약속 차단, 직원 승인 (#11)

**Q. AI API가 죽으면?**
- 접수와 진단을 분리, 타임아웃 후 "사람 확인 필요", 가짜 구현으로 시연 가능 (#10)

**Q. AI가 짠 코드를 어떻게 검증했나요?**
- 테스트 먼저 작성(TDD), 규칙별 단위 테스트, 컨테이너 통합 테스트, 코드 리뷰
- 실제 사례(#1): 리뷰를 표준과 스펙 두 축으로 나눠 돌렸다. 한 번도 연결 안 된 게이트웨이를 OFFLINE으로 시작하는 코드를 잡았다. 그대로 두면 설치도 안 된 현장에 오프라인 이상이 생긴다 → PENDING 상태 추가
- 실제 사례(#1): 테스트가 현장 1의 장비만 확인하던 빈틈을 잡아 세 현장 모두 확인하게 했다
- 실제 사례(#1): 장비와 게이트웨이가 서로 다른 현장을 가리킬 수 있는 구조를 복합 외래키로 막고, 잘못된 INSERT가 실제로 거부되는지 확인했다

**Q. (#10) AI 소견을 만드는 동안 A/S 신청 응답은 어떻게 하나요?**
- 저장만 하고 바로 "접수됨"으로 응답. 커밋 뒤 별도 스레드(@Async)에서 상황 요약 → AI → 검증
- AI 호출 중에는 DB 트랜잭션을 열지 않음(느린 외부 호출이 DB 연결을 붙잡지 않게)
- 서버가 도중에 꺼지면? 신청이 접수됨으로 남아 있고, 한 줄 UPDATE로 "맡은 시각"을 찍어 두므로 오래된 건만 재처리 스케줄러가 다시 맡음

**Q. (#10) 개인정보는 어떻게 지키나요?**
- 이름·연락처는 별도 컬럼, AI 입력에 아예 넣지 않음. 현장 이름도 빼고 지역·면적·인원·모델만
- 고객이 문의 글에 직접 쓴 전화번호·이메일은 [연락처]로 가림(흔한 형식만, 완벽하지 않다고 인정)
- AI에 보낸 입력 사본을 저장해서 "무엇을 보냈는지" 나중에 확인 가능

**Q. (#10) 검증에 걸리면?**
- 1회 재시도, 그래도 실패하면 "사람 확인 필요" + 이유(없는 부품, 없는 근거, 금지 표현, 형식 오류)를 남김. 직원이 처음부터 판단
- 시도마다 기록하므로 "첫 시도는 틀렸고 두 번째는 통과" 같은 품질 추이를 볼 수 있음

**Q. (#11) AI 소견이 틀리면 어떻게 되나요?**
- 고객에게 바로 나가지 않는다. 직원이 그대로 판정, 고쳐서 판정, 처음부터 판정 중 하나를 해야만 고객 안내가 확정된다
- 고친 항목을 서버가 기록 → AI가 자주 틀리는 부분을 데이터로 확인하고 프롬프트·기준표를 고친다(#12 평가 세트와 연결)

**Q. (#11) 두 직원이 같은 신청을 동시에 판정하면?**
- 신청 행 잠금(SELECT ... FOR UPDATE)으로 한 줄로 세우고, 뒤에 온 쪽은 "이미 판정된 신청"으로 409. 유니크 제약이 한 번 더 막는다

**Q. (#12) 왜 이 모델을 썼고, AI 품질은 어떻게 재나요?**
- 기본 Claude Opus 5.5(effort medium). 모델·effort·재시도 모델은 설정값이라 평가 세트로 비교해서 고른다
- 평가 세트: 정답이 있는 상황 요약 5개 × 3번, 1순위 원인 분류 정답률·검증 통과율·응답 시간·비용을 기록. 모델이나 프롬프트를 바꿀 때마다 다시 돌린다(스펙 A3 대응)
- 채점은 원인 분류(정해진 8가지)로 해서 채점용 AI 없이 정확하게

**Q. (#12) AI 응답 형식이 깨지면?**
- 1차: API의 구조화 출력이 JSON 스키마를 강제. 2차: 우리 검증기가 근거·부품·금지 표현 확인. 걸리면 재시도, 그래도 안 되면 사람 확인 필요
- 거절·응답 잘림은 HTTP 200이어도 실패로 보고 코드(REFUSAL, TRUNCATED)를 따로 남긴다

**Q. (#12) 비용은 어떻게 관리하나요?**
- 신청 한 건에 수 센트 수준. 숫자 계산은 코드가 해서 입력이 작다. 시스템 프롬프트는 캐싱
- 단계적 승격을 설정으로 지원: 싼 모델 먼저, 검증 실패 시 강한 모델. 켤지는 평가 숫자로 결정
- 테스트는 가짜 AI만, 실제 호출은 평가 명령에서만

## 8. 배포와 업데이트

**Q. 기능이 바뀌면 하드웨어도 업데이트해야 하나요?**
- 판단 로직은 서버에 두어 대부분 서버 배포로 끝낸다
- 게이트웨이는 버전과 지원 기능을 보고, 메시지는 필드 추가만 허용해 구버전과 공존
- 펌웨어 업데이트는 단계적 배포와 롤백 구조 (#15)

**Q. 장비가 수천 대로 늘면 어떻게 확장하나요?**
- 흐름(받기 → 검증 → 저장 → 조회)은 그대로 두고 상자를 늘리고 나눈다
- 브로커: 단일 Mosquitto → 클러스터나 매니지드(AWS IoT Core 등) (스펙 C12)
- 수신: 브로커 뒤에 Kafka 같은 큐를 두어 수신과 처리를 분리, 서버 여러 대는 shared subscription (C13)
- 저장: 일반 테이블 → 파티셔닝이나 TimescaleDB, 원본 90일 후 집계 (D6)
- 명령: 원하는 상태 + 만료 → 디바이스 섀도 (ADR-0002)
- 운영: 장비 인증서·TLS, 로그·지표 모니터링, 배포 자동화
- 지금은 11명 회사 규모에 맞게 단순하게 시작하고, 바꿀 지점을 미리 문서로 정해 두었다 (#52)

## 9. 기술 선택

**Q. 왜 Java 17, Spring Boot 3.x인가요?**
- 현업에서 가장 많이 쓰는 LTS, 21의 기능(가상 스레드)이 지금 규모에서는 필요 없다
- 장비 수천 대로 동시 연결이 병목이 되면 검토 (#3~#4)

**Q. 이 기술은 왜 골랐나요? (브로커, 대시보드 등)**
- 구현하면서 트레이드오프를 비교해 정한 결과를 ADR에 기록하고 여기에 요약할 것

## 10. 용어와 문서화

**Q. 비개발 직군과 같은 말을 쓰기 위해 한 일이 있나요?**
- 용어집(GLOSSARY.md)을 만들었다. 한 단어에 한 뜻, 비슷한 이름 피하기 원칙
- 회사가 쓰는 말을 따랐다: "현장", "A/S 신청"(홈페이지 메뉴 이름)
- 용어 때문에 생긴 버그를 미리 잡았다: 게이트웨이를 장비로 묶으면 공유기만 꺼져도 환기장치가 "오프라인"으로 보인다 → "확인 불가"로 분리 (#23~#27)

**Q. 설계 결정은 어떻게 남겼나요?**
- ADR 6건. 되돌리기 어렵고, 맥락 없이 의아하고, 대안 비교가 있었던 결정만 남겼다
- 예: 후드 연동은 현장 처리(0001), 원격 명령은 원하는 상태 + 만료(0002), AI 소견은 판정 없이 고객에게 안 나감(0005)

## 11. 인재상

**Q. "무엇을 만들까"보다 "왜 필요한가"를 고민한 경험은?**
- 공고 분석 → 회사 제품·서비스 조사 → 고객이 문의하기 전엔 상태를 모른다는 문제 정의 → MVP

**Q. 비개발 직군과 어떻게 소통하나요?**
- 오프라인 화면 문구를 고객 입장에서 설계("환기장치는 계속 동작 중이에요")
- 기술적 한계를 리스크 표로 투명하게 정리 (#11, #12)
