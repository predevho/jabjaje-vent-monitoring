# AI 소견은 커밋 뒤 전용 스레드에서 만들고, 할 일 목록은 DB의 접수됨 상태로 둔다

A/S 신청을 저장하면 고객에게 바로 접수됨으로 응답하고, AI 소견은 커밋 뒤 전용 작업 스레드(`@Async("assessmentExecutor")`, 2개)에서 만든다(#10). AI 호출은 수 초에서 수십 초가 걸려서, 요청 스레드에서 기다리면 고객 응답이 늦고 웹 서버 스레드가 묶인다.

ADR-0013은 측정값 → 이상 평가에서 `@Async`를 기각했다. 그쪽은 평가가 몇 밀리초라 같은 스레드에서 돌려도 되고, 순서와 단순함이 더 중요했다. AI 소견은 느린 외부 호출이라 반대다.

## 유실과 중복 처리

작업 스레드의 대기열은 메모리에 있다. 서버가 꺼지거나 대기열이 가득 차면 일이 사라진다. 그래서 **할 일 목록은 메모리가 아니라 DB**에 둔다. 소견이 끝나기 전까지 신청은 `RECEIVED`로 남고, 60초 주기 재처리가 "접수된 지 2분 넘게 지났는데 아직 접수됨"인 신청을 다시 처리한다.

두 곳(접수 직후 처리, 재처리)이 같은 신청을 잡지 않도록 한 줄 UPDATE로 맡는다.

```sql
UPDATE service_request SET assessment_started_at = :now
WHERE id = :id AND status = 'RECEIVED'
  AND (assessment_started_at IS NULL OR assessment_started_at < :now - 2분)
```

결과가 1인 쪽만 처리한다. PostgreSQL은 같은 행의 UPDATE를 한 줄로 세우므로 한 곳만 1을 받는다. 맡은 서버가 도중에 꺼지면 2분 뒤 다른 쪽이 다시 맡는다. 이 2분은 AI 호출 대기 시간(30초) × 시도 수(2)보다 길어야 한다. (#12에서 실제 Claude의 생각 시간과 SDK 재시도에 맞춰 시도 한 번 최대 3분, 재처리 기준 7분으로 늘렸다. ADR-0016) 짧으면 아직 처리 중인 신청을 다시 맡는다. 앱을 시작할 때 설정을 검사한다. 그래도 겹치면 `UNIQUE(service_request_id, attempt)`가 두 번째 저장을 막고, 막힌 쪽은 손을 뗀다.

AI를 부르는 동안에는 DB 트랜잭션을 열어 두지 않는다. 맡기, 시도 저장, 상태 변경을 각각 짧은 트랜잭션으로 나눈다.

## Considered Options

- **요청 안에서 동기로 호출**: 가장 단순하지만 고객이 AI를 기다리고, AI가 느리면 웹 서버 스레드가 모자란다. 기각.
- **메시지 큐(RabbitMQ, Kafka, Redis Stream)**: 재시도·유실 방지를 큐가 해 주지만 운영할 것이 하나 더 는다. A/S 신청은 하루 수십 건이라 DB 상태로 충분하다. 신청이 많아지거나 서버를 여러 대로 늘리면 다시 검토한다. 기각.
- **`SELECT ... FOR UPDATE SKIP LOCKED`로 일감 가져오기**: 여러 작업자가 일감을 나눠 가질 때 좋다. 지금은 신청 ID가 이미 정해진 채로 오므로 한 줄 UPDATE가 더 짧다. 기각.
- **메모리 대기열만 사용(재처리 없음)**: 서버 재시작 때 접수됨으로 영영 남는 신청이 생긴다. 기각.

## Consequences

- 고객 응답은 AI와 상관없이 빠르다. 대신 화면은 접수됨 → 소견 완료로 바뀌는 것을 다시 불러와서 보여 줘야 한다(2초 폴링).
- 서버가 꺼졌다 켜지면 소견은 최대 2분 + 재처리 주기(60초) 늦어진다.
- 신청 하나의 시도는 최대 2번이다. 다시 맡아도 이미 한 시도 수를 빼고 남은 만큼만 하고, 이미 통과한 시도가 있으면 상태만 마무리한다.
- 재처리는 스케줄러 스레드에서 AI를 직접 부르지 않고 작업 스레드에 넘긴다. 스케줄러 스레드는 다른 기능의 검사(게이트웨이 무수신, 후드 연동, 명령 재시도)와 함께 쓰기 때문이다.
- 대기열이 가득 차면 버리고 로그만 남긴다. 신청은 접수됨으로 남아 재처리가 줍는다.
