# 진입점마다 모듈을 나누고, 패키지는 `vent` 한 단계 아래 기능 → 레이어로 나눈다

서버 앱과 가상 게이트웨이(시뮬레이터)는 진입점이 다르므로 저장소 루트에서 `server/`, `simulator/`로 나눈다. 폴더 이름만 보고 무엇을 실행하는지 알 수 있게 하기 위해서다. 패키지는 관례적인 역도메인 이름(`io.github.predevho.vent`) 대신 `vent` 한 단계로 둔다. 역도메인 이름은 외부에 배포하는 라이브러리의 이름 충돌을 막는 장치인데, 이 프로젝트는 배포하지 않는 실행 앱이라 그 단계가 하는 일 없이 깊이만 늘린다. Spring Boot는 진입점을 기본 패키지에 둘 수 없으므로 한 단계는 유지한다.

`vent` 아래는 먼저 용어집의 기능 단위(`site/`, `telemetry/`, `anomaly/`)로 나누고, 각 기능 안에서 레이어(`controller/`(HTTP), `listener/`(MQTT 메시지), `service/`, `repository/`, `domain/`(enum은 `domain/type/`), `dto/request/`, `dto/response/`)로 나눈다. 관련 코드는 기능 폴더 한곳에 모이고, 기능 안에서는 역할이 폴더로 드러난다. 엔티티는 테이블마다 파일 하나, 응답 DTO는 record마다 파일 하나로 둔다. 자세한 규칙은 CLAUDE.md의 Coding standards에 있다.

## Considered Options

- **역도메인 패키지 유지**: 관례를 지키지만 진입점까지 9단계가 된다. 기각.
- **회사 이름 패키지(`jabjaje.vent`)**: 회사 코드처럼 보일 수 있다. 기각.
- **`src/main/java` 경로 변경**: Gradle, IDE, Docker 빌드의 기본 경로라 바꾸면 설정이 여러 곳에서 늘어난다. 유지.
- **기능 패키지만 두고 레이어 폴더 없음**: 처음 결정. 파일이 적을 때는 가장 얕지만, 기능 안에서 컨트롤러·서비스·엔티티·DTO의 역할이 폴더로 드러나지 않는다. 사용자 요청으로 2026-10-23에 기능 → 레이어로 바꿨다.
- **레이어 → 기능(`vent/controller/...`, `vent/service/...`)**: 기능이 늘수록 한 폴더에 관계없는 파일이 쌓이고, 기능 하나를 고치려면 여러 폴더를 오가야 한다. 기각.

## Consequences

- 레이어 사이에서 클래스를 참조하므로 패키지 전용(package-private) 대신 `public`을 쓴다.
- 이 코드를 라이브러리로 외부에 배포하게 되면 역도메인 패키지로 바꿔야 한다.
- 서버와 시뮬레이터가 같이 쓰는 메시지 형식이 생기면 `vent` 아래 공유 패키지나 별도 공유 모듈로 둔다.
