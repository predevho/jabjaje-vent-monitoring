# 수신 확인은 처리가 끝난 뒤 직접 보내고, 잠깐의 실패는 재연결로 다시 받는다

MQTT QoS 1에서 Paho는 기본적으로 메시지 처리 콜백이 끝나면 브로커에 수신 확인(PUBACK)을 자동으로 보낸다. 그래서 저장 중 DB 오류가 나도 확인이 나가고, 브로커는 메시지를 지워서 그 측정값은 사라졌다(#2 리뷰에서 발견, 스펙 9.1 C15). 수동 확인 응답(manual ack)으로 바꿔, 처리기가 "처리 끝(DONE)"이라고 할 때만 확인을 보낸다. DB 연결 실패처럼 잠깐의 문제면 "나중에(RETRY_LATER)"를 돌려주고 확인을 보내지 않는다. MQTT는 확인을 못 받은 메시지를 **재연결할 때만** 다시 보내므로, 5초 뒤 연결을 끊고 같은 세션으로 다시 연결한다. 같은 메시지가 다시 와도 messageId 중복 무시 저장이 있어 한 번만 저장된다(최소 한 번 전달 + 멱등 저장).

## 실패 구분

| 실패 | 예 | 처리 |
|---|---|---|
| 다시 해도 안 되는 것 | JSON 형식 오류, 장비 ID 불일치, 미등록 장비, 무결성 위반 같은 그 밖의 `DataAccessException`, 예상하지 못한 예외(버그) | 확인을 보내고 버린다(로그). 다시 받으면 같은 메시지가 끝없이 돌아온다(poison message) |
| 잠깐의 문제 | `TransientDataAccessException`, `DataAccessResourceFailureException`(DB 연결 실패), `TransactionException` | 확인을 보내지 않고 재연결해서 다시 받는다 |

처음에는 `DataAccessException` 전체를 잠깐의 문제로 봤다. 코드 리뷰에서 센서 고장값(습도 65535)이 컬럼 크기를 넘으면 무결성 위반이 나고, 그 메시지를 5초마다 끝없이 다시 받으며 재연결 때마다 다른 현장 수신까지 끊긴다는 것을 찾았다. 그래서 잠깐의 문제를 위 세 가지로 좁히고, 온도·습도 컬럼도 넓혔다(V5).

## Considered Options

- **자동 확인 유지 + 실패한 메시지를 서버 메모리에 보관했다가 재시도**: 서버가 죽으면 메모리의 메시지도 사라진다. 기각.
- **실패한 메시지를 별도 테이블(dead letter)에 저장**: DB가 죽은 상황이라 저장할 곳이 없다. 기각.
- **수동 확인 + 재연결**: 채택. 메시지를 브로커에 그대로 두므로 서버가 죽어도 안전하다.

## Consequences

- DB가 오래 죽어 있으면 5초마다 재연결을 반복한다. 확인을 못 받은 메시지가 브로커의 동시 전송 한도(inflight)만큼 쌓이면 브로커가 더 보내지 않아 자연스럽게 속도가 조절된다.
- 다시 받은 메시지는 수신 시각이 늦어져 늦은 측정값으로 표시될 수 있다. 실제로 서버가 늦게 받았으므로 맞는 동작이다. 용어집의 "늦은 측정값"을 원인이 아니라 측정 시각과 수신 시각의 차이로 정하도록 고쳐 이 경우도 포함했다.
- 이미 연결이 끊겨 있으면 직접 재연결하지 않는다. Paho 자동 재연결이 다시 붙을 때 브로커가 다시 보내 주고, 둘이 동시에 연결하면 부딪히기 때문이다. Paho 자동 재연결 간격은 기본값(최대 2분)이 너무 길어 최대 30초로 줄였다.
- 처리기를 새로 만들 때 실패가 "다시 하면 되는 것"인지 반드시 구분해야 한다(`MqttMessageHandler` 문서).
