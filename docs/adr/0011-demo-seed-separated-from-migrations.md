# 시연용 시드 데이터는 운영 마이그레이션과 분리해 demo 프로필에서만 넣는다

처음에는 시연용 현장 3곳을 `db/migration/V2__seed_sites.sql`로 넣었다. 이대로 실제 서버에 배포하면 운영 DB에 가짜 현장(양평, 안성, 서대문)이 들어간다. 그래서 시드를 `db/seed/R__demo_seed.sql`로 옮기고, 기본 설정은 `db/migration`만, `demo` 프로필(Docker Compose, 통합 테스트)은 `db/seed`까지 읽게 했다. 시드는 Flyway 반복 실행 마이그레이션(`R__`)이다. 모든 버전 마이그레이션 뒤에 실행되고 내용이 바뀌면 다시 실행되므로, `ON CONFLICT DO NOTHING`으로 여러 번 실행해도 결과가 같게(멱등) 만들었다.

## Considered Options

- **V2를 그대로 두기**: 규칙("커밋된 마이그레이션은 고치지 않는다")은 지키지만 운영에 가짜 데이터가 들어간다. 기각.
- **시드를 버전 마이그레이션으로 별도 위치에 두기(`db/seed/V2__...`)**: 프로필로 나눌 수는 있지만, 스키마 버전 번호와 시드 번호가 섞여 순서를 관리하기 어렵다. 기각.
- **애플리케이션 코드(CommandLineRunner)로 넣기**: 프로필로 나누기 쉽지만 SQL보다 길고, 스키마 변경과 시드의 실행 순서를 Flyway가 보장하지 않는다. 기각.

## Consequences

- 이미 커밋된 V2를 옮긴 것은 "커밋된 마이그레이션은 고치지 않는다" 규칙의 예외다. 아직 어디에도 배포하지 않았고 로컬 DB만 다시 만들면 되는 시점이라 허용했다. 배포 이후에는 이렇게 할 수 없다.
- 기존 로컬 DB는 V2 기록이 남아 있어 Flyway 검증에 실패하므로 한 번 지우고 다시 만든다(`docker compose down -v`).
- 시드가 필요한 테스트는 `@ActiveProfiles("demo")`를 붙인다.
