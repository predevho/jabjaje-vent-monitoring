# 게이트웨이 상태 변경과 오프라인 이상은 같은 트랜잭션에서 처리한다

게이트웨이 연결 상태가 바뀌면 `GatewayConnectionService`가 `GatewayConnectionChangedEvent`를 발행하고, 이상 기능이 받아서 `GATEWAY_OFFLINE` 이상을 열거나 닫는다(#6). 측정값 → 이상 평가(ADR-0013)와 달리, 이 이벤트는 **커밋 후가 아니라 같은 트랜잭션 안에서** 처리한다(`@EventListener`). 받는 쪽 서비스는 `Propagation.MANDATORY`라 트랜잭션 밖에서는 부를 수 없다.

같은 이벤트 방식인데 반대로 정한 이유는 무엇이 더 중요한지가 다르기 때문이다.
- **측정값(ADR-0013)**: 측정값이 이상보다 중요하다. 이상 평가가 실패해도 측정값은 남아야 한다. 평가는 DB의 최신 값을 다시 읽으므로 다음 측정값이 오면 따라잡는다.
- **연결 상태(이 ADR)**: 상태와 이상이 항상 같이 움직여야 한다. 상태만 오프라인으로 커밋되고 이상 저장이 실패하면, 다음 무수신 검사는 "이미 오프라인"이라 이상을 다시 만들지 않는다. 그 이상은 영영 빠진다. 같은 트랜잭션이면 이상 저장이 실패할 때 상태 변경도 롤백되고, 다음 검사(30초 뒤)에서 둘 다 다시 시도된다.

## 동시 수정

측정값 수신(MQTT 스레드)과 무수신 검사(스케줄러 스레드)가 같은 게이트웨이 행을 바꾼다. 검사가 "2분 지남"을 읽은 직후 측정값이 "연결됨"으로 커밋되면, 검사가 그 위에 "일시 끊김"을 덮어쓸 수 있다(lost update). 두 경로 모두 행 잠금(`SELECT ... FOR UPDATE`)으로 읽고, 잠근 뒤 엔티티 메서드에서 조건을 다시 확인한다. 잠금은 DB에 걸리므로 서버가 여러 대여도 그대로 통한다.

## Considered Options

- **커밋 후 이벤트 + 새 트랜잭션(ADR-0013과 같게)**: 위에서 말한 대로 상태와 이상이 어긋날 수 있다. 기각.
- **게이트웨이 서비스가 이상 저장소를 직접 호출**: 같은 트랜잭션이 되지만 게이트웨이 기능이 이상 기능을 알아야 한다. 이벤트로 의존 방향을 지킨다. 기각.
- **Redis + Lua 스크립트로 원자적 처리**: 상태와 이상이 둘 다 PostgreSQL에 있어 트랜잭션 하나로 이미 원자적이다. Redis를 넣으면 두 저장소에 나눠 쓰게 되고, Lua는 Redis 안에서만 원자적이라 한쪽만 성공하는 문제(dual write)가 새로 생긴다. 기각. 장비가 수만 대로 늘어 측정값마다 `last_received_at`을 DB에 쓰는 것이 부담이 되면, 마지막 수신 시각만 Redis Sorted Set에 두고 상태가 바뀔 때만 DB에 쓰는 방식을 다시 검토한다.
- **낙관적 잠금(`@Version`)**: 충돌하면 재시도해야 한다. 현장 3곳, 30초 주기라 잠금 대기가 거의 없어 비관적 잠금이 더 단순하다. 기각.

## Consequences

- 이상 기능에서 예외가 나면 그 게이트웨이의 상태 변경도 롤백된다. 측정값 경로(`GatewayTelemetryStoredListener`)에서는 로그만 남고, 측정값은 이미 저장돼 있다. 다음 측정값에서 다시 반영된다.
- 무수신 검사는 게이트웨이마다 트랜잭션을 따로 쓴다. 한 게이트웨이의 이상 저장이 실패해도 다른 게이트웨이의 상태 변경은 롤백되지 않고, 잠금도 하나씩 짧게 잡힌다. 한 게이트웨이 안에서는 상태와 이상이 함께 커밋되거나 함께 롤백된다.
- 검사가 먼저 잠그면 그 직후 들어온 측정값은 검사가 끝난 뒤 반영된다. 그래서 오프라인으로 바꾸고 이상을 연 직후 해결되는 일이 드물게 생길 수 있다. 기준(30분) 근처에서만 생기고 결과는 맞아서 그대로 둔다.
- 서버를 여러 대 띄우면 검사도 여러 대에서 돈다. 잠금 덕분에 결과는 맞지만 같은 일을 여러 번 한다. 그때는 ShedLock 같은 스케줄러 잠금을 둔다.
